## 一、修复：手动转移绕过闸门，导致状态与检查点脱节

### 1.1 现象

```
09:52:18 [intent] intent=INTERVIEW_REPLY | sub=改期/提出新时间 | conf=0.96
09:52:18 [notify] 中断点不是等待候选人回复，不恢复图 | candidate_id=Jff3UBXcsTuAQZtFZfGWYA
```

候选人回复了改期，流程没反应。

### 1.2 根因

排查该候选人后发现**状态自相矛盾**：

| 事实 | 值 |
|---|---|
| 检查点 `next` | `('manual_decision',)` —— 图还停在人工闸门 |
| `email_invite_sent_at` | **None** —— 邀请邮件从未发出 |
| 链尾 | `AI筛选成功`（活跃） |
| `candidates.status` | **面试时间协商中** —— 与上面全部矛盾 |

`面试时间协商中` 不是流程写的，是**从前端手动改的**：转移表允许
`待人工确认 → 面试时间协商中`。这条转移**绕过闸门、也不发邀请**
（只有 `人工通过/重试` 会触发 `trigger_manual_retry`），于是状态说在协商、
检查点还停在闸门、邀请没发。候选人不知从哪看到邀约便回复了改期。

`notify` 拒绝 resume 是**正确**的——确实没有「等待候选人回复」这个中断点。

### 1.3 修复

`ALLOWED_TRANSITIONS[PENDING_MANUAL_DECISION]` 去掉 `NEGOTIATING`，只保留淘汰：

```python
CandidateStatusEnum.PENDING_MANUAL_DECISION: {
    CandidateStatusEnum.AI_FILTER_FAILED,
},
```

要推进只能走闸门的 approve——它会自己写「面试时间协商中」并去发邀请。
前端转移表同步（去掉这个手动入口）。

### 1.4 数据修正

候选人 `Jff3UBXcsTuAQZtFZfGWYA`（张明远 / 15613156721@163.com）状态改回
**待人工确认**。检查点仍停在 `manual_decision`，HR 可在列表点「发送邮件」继续。

## 二、回复兜底 + 不可用回信的备选时段

### 2.1 候选人回复但流程不在等待 → 落复核，不再丢弃

§一 暴露的缺口：候选人回复了、但流程不在「等待回复」中断点时，
`notify` 只记一行日志就把邮件丢了。

改动：`_resume_candidate_graph()` 改为返回 `bool`（True=已发起恢复）。
`notify()` 在 `INTERVIEW_REPLY` 分支里，未恢复时调用 `_enqueue_human_review()`
落进 `mail_reviews`，HR 在「意图复核」页能看到并处理。

### 2.2 时段不可用回信也列备选时段

原来 `_notify_candidate_slot_unavailable()` 只说「您提的时间面试官无法安排，
麻烦再提供一到两个时间」——候选人只能再猜一个，来回一轮就是一天。

现在和 `email_invite` 一致，附上面试官近期可用时段（最多 3 段）：

```
感谢您的回复。您提出的面试时间（2026-11-20 16:00）面试官暂时无法安排。
面试官近期有以下时间段可供面试（按时间先后）：
1. 2026-11-20 09:00 - 2026-11-20 10:00
2. ...
请您回复方便的时间（例如「确认」表示第一个时间段）。
如果以上都不方便，请回复您方便的时间，我们将会重新协商面试时间。
```

新增 `_load_alternative_slots(state)`：查不到时段（钉钉故障等）时返回空串，
正文退回原措辞——备选时段是增强项，不能拖垮回信。

## 三、意图复核 `evidence` 脏数据

### 3.1 现象

复核详情里出现：

```json
{ "evidence": ":[", "intent_guess": "INTERVIEW_REPLY", "confidence": 0.9 }
```

### 3.2 根因

`evidence` 直接来自 LLM 的结构化输出，代码没有任何加工。而 system prompt 里
只写了字段名列表（`...evidence...`），**没有定义它该放什么**——模型于是把
JSON 结构碎片当成了「片段」。

### 3.3 修复（三层）

1. **prompt 明确语义**：`evidence` 必须是【邮件正文】里支撑该判定的**连续原文片段**
   （≤50 字），不要输出 JSON 结构、符号或换行，找不到就留空；
2. **`MailIntentResult` 加 `field_validator`**：去掉首尾空白后，
   长度 <4 或**不含任何文字**（字母/数字/汉字）的一律置空，否则截断到 200 字；
3. **清洗历史数据**：

```sql
UPDATE mail_reviews SET evidence = ''
WHERE length(evidence) < 4
  AND evidence !~ '[[:alnum:]]'
  AND evidence !~ '[一-龥]'
```

已清洗 1 条。

清洗效果：

```
':['            -> ''
'{...}'         -> ''
'下午2点可以吗'  -> '下午2点可以吗'
'甲'*500        -> 截断到 200
```

## 四、检查点存储改用连接池

### 4.1 背景

`checkpointer.py` 原来是「进程级单条 `AsyncConnection`」：

```python
conn = await AsyncConnection.connect(pg_url, autocommit=True, ...)
saver = AsyncPostgresSaver(conn=conn, ...)
```

而 psycopg 的 `AsyncConnection` **不是协程安全的**（同一时刻只能执行一个操作）。
当前不出错，是因为 `AsyncPostgresSaver` 内部用 `asyncio.Lock` 串行化了所有 DB 操作
（见其 `_cursor()` 里的 `async with self.lock`）。但单连接有明显短板：

- 连接断开后**不会自愈**，只能重启进程；
- 无健康检查、无坏连接替换；
- 所有 checkpoint 读写强制串行，扩展性差。

### 4.2 改造

改用 `psycopg_pool.AsyncConnectionPool`：

```python
pool = AsyncConnectionPool(
    conninfo=pg_url,
    min_size=settings.CHECKPOINT_DB_MIN_SIZE,   # 默认 1
    max_size=settings.CHECKPOINT_DB_MAX_SIZE,   # 默认 2
    kwargs={
        "autocommit": True,
        "prepare_threshold": 0,
        "row_factory": dict_row,
    },
    open=False,
)
await pool.open()
saver = AsyncPostgresSaver(conn=pool, serde=_build_serde())
await saver.setup()
```

### 4.3 新增配置（`app/core/config.py`）

| 配置项 | 默认 | 说明 |
|--------|------|------|
| `CHECKPOINT_DB_MIN_SIZE` | 1 | 连接池最小连接数 |
| `CHECKPOINT_DB_MAX_SIZE` | **2** | 连接池最大连接数（串行场景下 2 足够） |

**为什么上限只给 2：**

`AsyncPostgresSaver` 内部有 `asyncio.Lock`，checkpoint 读写是**串行**的，
池的并发能力根本用不上。给 10 条连接纯属浪费数据库资源。
保留 2 条是为了：1 条活跃 + 1 条冗余（坏连接替换 / 健康检查时备用）。

### 4.4 收益与定位

| 维度 | 结论 |
|------|------|
| **并发吞吐** | ❌ 无提升（LangGraph 实例锁是瓶颈，串行执行） |
| **连接可靠性** | ✅ 断线自愈、健康检查、坏连接替换 |
| **资源占用** | ✅ 最多 2 条连接（原来单连接，现在略增但可控） |
| **未来扩展** | ⚠️ 若改为「多 saver 实例」才可能真并发 |

> **准确定位**：连接池在这里是**可靠性保障**，不是性能优化。

## 五、`recheck_interview_slot` 校验时段是否已过去

### 8.1 问题

复核节点只判断「面试官该时段是否仍空闲」，不判断**这个时间是不是已经过去了**。
协商拖过周末/假期时，候选人可能确认一个已经过去的时间 —— 查钉钉会返回
「那天有档期」，于是流程把面试排到过去。

### 8.2 修复

`recheck_interview_slot_node` 在查钉钉**之前**先比较：

```python
now = now_beijing()
if proposed_dt <= now:
    # 直接按「不可用」处理：轮次归零 + 重发约时间
```

不满足才去查钉钉（避免无谓的 API 调用）。

### 5.3 测试

新增 `test_past_slot_is_treated_as_unavailable`，并断言此时
**不会调用** `get_user_available_slots`（用会抛异常的替身验证）。

> 顺带修了测试夹具：`PROPOSED` 原本写死 `2026-11-20 10:30`，
> 过了那天整组测试就会因新校验集体变红。改为 `now_beijing() + 48h`。

## 六、`alembic/env.py` 配 `include_object`

### 8.1 问题

`--autogenerate` 把 LangGraph 自己管理的 checkpoint 表
（`checkpoints` / `checkpoint_blobs` / `checkpoint_writes` / `checkpoint_migrations`）
当成「库里有、模型里没有」，生成 **DROP TABLE** 语句 —— 执行等于清空所有流程检查点。
`alembic_version` 同理（Alembic 自己的版本表）。

### 8.2 修复

```python
_EXCLUDED_TABLES = frozenset({
    "checkpoints", "checkpoint_blobs", "checkpoint_writes",
    "checkpoint_migrations", "alembic_version",
})

def include_object(object, name, type_, reflected, compare_to):
    if type_ == "table" and name in _EXCLUDED_TABLES:
        return False
    return True
```

注入 offline / online 两处 `context.configure`。空跑验证：生成结果里
**不再出现任何 checkpoint 相关或 `drop_table` 语句**。

## 七、`skip_scoring` 权限收紧到 HR 以上

### 8.1 问题

`POST /candidate/create` 只要登录即可，任何员工都能勾选「跳过筛选与 AI 评分」，
等于绕过 AI 评估直接发邀请。

### 8.2 修复

```python
if candidate_data.skip_scoring and not (current_user.is_hr or current_user.is_superuser):
    raise HTTPException(status_code=403, detail="仅 HR / 超管可跳过 AI 筛选与评分")
```

普通员工传 `skip_scoring=True` 直接 403；HR / 超管不受影响。

## 八、终态节点单独写链

### 8.1 问题

`screening` / `rejected` / `refused` / `negotiation_expired` / `error`
只改 `candidates.status`，链表里没有对应记录 —— 状态变更的**中间过程**断档，
只有 `archive_node` 补的一条链尾。

### 8.2 修复

新增统一 helper `terminal_records.record_node_transition(candidate, position, to_status)`：

- `candidates.status` + 状态变更链**同一事务**写入；
- **去重**：链上最新记录已经是该状态时就不再插一条
  （否则 `screening` 未通过 → `rejected` 会产生两条一模一样的 `AI筛选失败`）。

五个节点全部改用它：

| 节点 | 写入状态 |
|---|---|
| `screening_node`（失败） | AI筛选失败 |
| `rejected_node` | AI筛选失败 |
| `refused_node` | 拒绝面试 |
| `negotiation_expired_node` | 协商超时 |
| `error_node` | 处理异常 |

`screening_node` 是**第一次真正改状态**（此前只返回 `screening_passed=False`，
由 `rejected_node` 去改），现在筛选未通过这一事实在链里可追溯。
