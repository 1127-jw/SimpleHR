# 变更记录 2026-11-19

本次主题：**工作流节点拆分 + 建日程前复核 + 人工闸门 + 一次线上事故修复**。
都围绕招聘状态图的正确性与可控性。

1. **每个节点一个文件**：`get_candidate_email_reply_node` / `rejected_node` /
   `refused_node` / `error_node` 从「多节点/多职责共用一个文件」里拆出来，
   发信收敛到 `mail_notify.py`。详见 §一；
2. **新增复核节点 `recheck_interview_slot`**：在「候选人确认时间」与「创建日程」
   之间再查一次面试官该时段是否仍空闲；被占用就**轮次归零 + 重发约时间邮件**，
   回到等待回复。详见 §一；
3. **人工闸门 `manual_decision` + 前端「发送邮件」**：评分通过后不再自动发邀请，
   先 `interrupt()` 暂停；候选人列表操作列出现条件渲染的「发送邮件」，
   点击唤醒图继续。详见 §二；
4. **线上事故修复**：评分 9 分却显示「AI筛选失败」、邀请信后 5 秒又收到
   「协商暂停」。两个独立缺陷叠加——PG 枚举缺 `待人工确认`，以及所有
   `interrupt()` 节点共用 resume 通道导致闸门被超时巡检误开。详见 §三。

## 一、节点拆分为单文件 + 新增复核节点

### 1.1 一个节点一个文件

`app/workflow/candidate_nodes/` 原本有两处「多节点/多职责共用一个文件」：

| 改前 | 改后 |
|---|---|
| `check_availability_node.py` 里塞着 `get_candidate_email_reply_node` | 独立 `get_candidate_email_reply_node.py` |
| `rejected_or_refused_nodes.py` 含两个节点 | `rejected_node.py` / `refused_node.py` |
| `error_node` 与 `node_error_wrapper` 同文件 | `error_node.py`；`error_handler.py` 只留装饰器 |

发信也顺手收敛：新增 `mail_notify.py:send_workflow_email()`，
`email_invite` 与新节点共用，不再各写一遍「取 bot + 连接 + 异常包装」。

> `check_availability_node` 的「时段不可用」与 `negotiation_expired_node` 的
> 「协商暂停」是 **best-effort** 通知（刻意不报错），仍各自包 try/except，
> 不走 `mail_notify`——它们的错误契约不同。

### 1.2 新增复核节点 `recheck_interview_slot`

**问题**：协商可能持续好几天，期间面试官完全可能在候选人确认的那个时段排了别的
日程。原流程 `check_availability → confirm` 直接建日程，会出现
「日程与面试官已有安排撞车」。

**新流程**：

```
check_availability ──REPLY_TIME_AVAILABLE──> recheck_interview_slot
                                              ├─ 仍空闲 ─> confirm（建日程 + 落库 + 发确认信）
                                              └─ 被占用 ─> 轮次归零 + 重发约时间邮件
                                                          └─> get_candidate_email_reply_node
```

要点：

- 复用 `resolve_interview_slot("hours", ...)` 按**确切时间**复核（不是「上午/下午」
  那种模糊提议），查询窗口与 `check_availability` 对齐；
- **轮次归零**是必要的：否则候选人刚被「确认」过一次，`negotiation_round`
  可能已接近上限，重新协商要从头给机会；
- 重发的那封邮件是「**重启协商**」的手段，不是可选通知——发不出去等于流程卡死，
  所以失败抛 `EmailSendError` 进 error 节点，而不是静默跳过；
- 被占用时写 `REPLY_SLOT_TAKEN`（`candidate_state.py`），路由靠它区分去向。

## 二、人工闸门 + 前端「发送邮件」

### 2.1 需求

原流程 `scoring → email_invite`：评分达标就**自动**发面试邀请。
现在要求在两者之间插一道人工闸门，由 HR 决定要不要发；前端在候选人管理页的
操作列提供「发送邮件」，点击后唤醒暂停的图。

### 2.2 后端

**新节点** `manual_decision_node`（同样**不加** `@node_error_wrapper`——
`interrupt()` 的 `GraphInterrupt` 会被包装器吞掉，图就永不暂停）：

```
scoring ──达标──> manual_decision ──approve──> email_invite
                        │                      └─reject──> rejected
                        └─ interrupt()
```

- 挂起前把候选人状态置为新增的 `PENDING_MANUAL_DECISION`（待人工确认）；
- `approve` → 状态回到 `AI筛选成功` → 继续走邀请；
- `reject` → 走 `rejected_node` 落 `AI筛选失败`；
- 新增常量 `MANUAL_DECISION_APPROVE` / `MANUAL_DECISION_REJECT`（就是 `"approve"`
  / `"reject"`，直接作为 `Command(resume=...)` 的值）。

**新端点** `POST /candidate/{id}/manual-decision`，body `{decision: "approve"|"reject"}`：

- 权限与 `PATCH /status` 一致（HR / 超管 + `get_for_user` 可见性）；
- 服务层 `resume_manual_decision()`：先 `aget_state` 确认**确实停在中断点**，
  再 `Command(resume=decision)`；不在待确认状态时抛 `StatusFlowError` → 400，
  避免对着已结束的 thread 乱发 resume；
- 与 `trigger_manual_retry()` 的区别：那个是 `Command(goto=...)` 另起一段流程，
  这个是 `Command(resume=...)` **唤醒已暂停的 interrupt**，检查点里的评分状态原样保留。

### 2.3 前端

- `candidate_api.ts`：状态枚举与转移表同步 `PENDING_MANUAL_DECISION`，
  新增 `submitManualDecision(id, decision)`；
- `candidates/index.vue`：操作列在 `status === 待人工确认` 时**条件渲染**
  「发送邮件」按钮 → 弹窗提供「发送邮件并继续 / 不发送，淘汰」两个动作；
  状态标签补 `待人工确认`（warning）。

> 按钮做成**条件显示**而不是常显：不在闸门状态时点击没有意义（后端也会拒绝）。
> 如果希望常显，去掉 `v-if` 即可。

### 2.4 一个 LangGraph 的坑（已记录在节点注释里）

`interrupt()` 所在的节点在 **resume 时会从头重跑**，所以闸门里
`_set_status(PENDING_MANUAL_DECISION)` 会执行两次。写的是同一个值、幂等无害；
这也是刻意不把别的副作用放在 `interrupt()` 之前的原因。

## 三、修复：评分达标却显示「AI筛选失败」+ 邀请信后紧跟「协商暂停」

线上两个现象，根因是**两个独立缺陷叠加**。

### 3.1 现象

1. 候选人评分 **9 分**（阈值 7），前端却显示 **AI筛选失败**；
2. 收到面试邀请邮件后 **5 秒**又收到「面试时间协商-已暂停」。

### 3.2 根因一：PostgreSQL 枚举缺值

`candidates.status` 是 `SQLAlchemyEnum(CandidateStatusEnum)` → **PG ENUM**
（不是 varchar）。§二 只在 Python 侧加了 `PENDING_MANUAL_DECISION`，
**没有同步到库**，于是闸门写状态直接报错（`logs/nodes.log`）：

```
sqlalchemy.exc.DataError: invalid input value for enum candidatestatusenum: "待人工确认"
UPDATE candidates SET status=%(status)s ... WHERE candidates.id = 'PQQAqpW4qib4yh98mJPgQR'
```

而闸门里 `_set_status` 把异常吞了（只记 error），后果很隐蔽：
状态仍是 scoring 写的「AI筛选成功」→ **前端看不到「发送邮件」按钮**。

### 3.3 根因二：所有 `interrupt()` 节点共用一个 resume 通道

`manual_decision_node` 用 `interrupt()` 挂起，而**超时巡检**用
`Command(resume="TIMEOUT")` 唤醒**邮件回复**中断点。两者的 resume 值不同，
但**中断点本身没有身份标识**——巡检只看「有没有中断点」：

```python
if not snapshot.interrupts:      # ← 有闸门的中断点也成立
    continue
await candidate_graph.ainvoke(Command(resume=EMAIL_REPLY_TIMEOUT), config)
```

于是时序变成：

```
10:16:09  评分 9 分 → 写「AI筛选成功」
10:16:09  闸门挂起（写「待人工确认」失败，被吞）
10:16:20  超时巡检用 TIMEOUT 误开闸门 → 走 reject 分支
10:16:20  rejected_node 写「AI筛选失败」          ← 现象 1
10:18:14  HR 点「人工通过/重试」→ 发邀请邮件
10:18:20  又被 TIMEOUT 误开 → negotiation_expired → 发「协商暂停」  ← 现象 2
```

**修复**：给中断点加身份标记，恢复方必须先自证身份。

- `candidate_state.py` 新增 `EMAIL_REPLY_INTERRUPT` / `MANUAL_DECISION_INTERRUPT`
  与 `is_waiting_on(interrupts, marker)`（认字符串或 `{"node": marker}` 两种入参）；
- `get_candidate_email_reply_node` 与 `manual_decision_node` 的 `interrupt()` 改用
  这两个常量做 value；
- `timeout_tasks.sweep_stale_email_replies` 只在
  `is_waiting_on(snapshot.interrupts, EMAIL_REPLY_INTERRUPT)` 时才 resume；
- `resume_manual_decision` 加**两道**校验：中断点身份 + 库里状态必须是
  `PENDING_MANUAL_DECISION`（防止状态与检查点不一致时误开）。

### 3.4 修复：枚举迁移

新增 `alembic/versions/b2c3d4e5f6a7_add_pending_manual_decision_to_candidatestatusenum.py`：

```python
op.execute("ALTER TYPE candidatestatusenum ADD VALUE IF NOT EXISTS '待人工确认'")
```

已在本机执行（`alembic upgrade head`），复核 PG 枚举共 13 个值、含「待人工确认」；
并对真实候选人调用 `_set_status(PENDING_MANUAL_DECISION)` 验证写库成功
（修复前必然抛 `DataError`）。

> 注意：`ALTER TYPE ... ADD VALUE` **不能回滚**（PG 不支持删枚举值），
> 但它是幂等的，且新增值不影响既有数据。

### 3.5 验证

```
251 passed
PG enum: ['已投递','AI筛选失败','AI筛选成功','待面试','拒绝面试','面试通过',
          '面试未通过','已入职','已拒绝','协商超时','处理异常','人工通过/重试','待人工确认']
```

新增 7 条回归测试：`is_waiting_on` 三种入参、**超时巡检不得 resume 人工闸门**
（本次事故的直接回归）、对照「等待候选人回复仍照常 resume」、
闸门 resume 的身份校验与状态校验。
