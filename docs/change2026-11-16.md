## 一、统一限流模块 `app/core/limiters.py`

两个 limiter 的公共部分（按 key 的进程内信号量 + 等待时长日志）完全一致，
差异只在"是否带 RPM 限速"和"池怎么分"，因此合并为一个模块。

### 1.1 取值依据（重要前提）

**厂商配额不是瓶颈**，因此不能用配额反推并发：

| 模型 | 厂商标称配额 |
|---|---|
| `deepseek-v4.1-flash` | RPM 15,000；TPM 1,200,000；并发 2,500 |
| `qwen3.8` 系列 | TPM 5,000,000 |

我们当前限制仅占配额的 **0.16%～0.4%**。所以限流目的是**保护本地资源 + 平滑突发**，
数值按本地容量定：

| 项 | 取值 | 依据 |
|---|---|---|
| `LLM_MAX_CONCURRENCY` | **20** | 本地 DB 连接池上限 30（`pool_size=10` + `max_overflow=20`）；等 LLM 不占连接 |
| `LLM_RPM_LIMIT` | **600** | 突发缓冲；远低于厂商 15,000 |
| `RECRUIT_TASK_MAX_CONCURRENCY` | **12** | 小于调用级上限，给解析/富化留 LLM 名额 |
| `RESUME_PARSE_MAX_CONCURRENCY` | **8** | OCR 为外部服务 |
| `MAIL_ENRICH_MAX_CONCURRENCY` | **2** | 后台任务，不阻塞用户 |

### 1.3 全文（`app/core/limiters.py`）

```python
"""统一限流：调用级（LLM）与任务级（Agent / 图流程 / 解析）。

两层限流共用同一套"按 key 的进程内信号量 + 等待时长日志"：

* **调用级** ``llm_slot``：额外做 RPM 滑动窗口（Redis）限速；
  所有 LLM 调用**共享同一个池**（内部 key 固定为 ``__llm__``），
  各调用点传入的 ``key`` 只用于日志与 RPM 分组，不各自成池。
* **任务级** ``task_slot``：按 ``key`` 分池（``recruit`` / ``resume_parse`` /
  ``mail_enrich``），限制同时运行的完整业务任务数。

分工：任务级保护下游副作用（钉钉日程 / 邮件 / DB 写），调用级保护模型服务压力。

注意：信号量是**进程内**的，仅在 ``gunicorn workers=1`` 下有效；
多 worker 部署需改为 Redis 信号量（RPM 那层已是 Redis，天然跨进程）。
"""
from __future__ import annotations

import asyncio
import logging
import time
from contextlib import asynccontextmanager

from app.core.config import get_settings
from app.core.redis_client import get_redis

logger = logging.getLogger(__name__)

# key -> Semaphore（进程内单例，懒创建）
_semaphores: dict[str, asyncio.Semaphore] = {}

# 等待超过该秒数才记 warning，避免正常排队刷屏
_WAIT_LOG_THRESHOLD_SECONDS = 1.0
# RPM 超限后的软等待（秒）：平滑突发，而不是直接失败
_RPM_SOFT_WAIT_SECONDS = 1.0

# 所有 LLM 调用共享的池 key（调用点传入的 key 仅用于日志与 RPM 分组）
_LLM_SLOT_KEY = "__llm__"


def _get_semaphore(key: str, limit: int) -> asyncio.Semaphore:
    if key not in _semaphores:
        _semaphores[key] = asyncio.Semaphore(limit)
    return _semaphores[key]


@asynccontextmanager
async def _acquire(key: str, limit: int, log_tag: str):
    """公共部分：占用一个名额并记录等待时长。"""
    started = time.monotonic()
    sem = _get_semaphore(key, limit)
    await sem.acquire()
    waited = time.monotonic() - started
    if waited > _WAIT_LOG_THRESHOLD_SECONDS:
        logger.warning(
            "[limit] 等待 %.2fs 才拿到名额 | key=%s | limit=%s", waited, log_tag, limit,
        )
    try:
        yield
    finally:
        sem.release()


async def _hit_rpm(key: str) -> bool:
    """滑动窗口记一次调用。

    Returns:
        True 表示放行；False 表示本分钟已超限。
        Redis 不可用时返回 True（降级为不限速）。
    """
    limit = get_settings().LLM_RPM_LIMIT
    if limit <= 0:
        return True
    try:
        from app.core.rate_limit import hit

        return await hit(get_redis(), key, limit=limit, window=60)
    except Exception:  # noqa: BLE001 - 限流是增强项，Redis 抖动不能拖垮业务
        logger.debug("LLM RPM 限速不可用（Redis 未就绪），本轮跳过", exc_info=True)
        return True


@asynccontextmanager
async def llm_slot(key: str = "llm:default"):
    """调用级：占用一个 LLM 调用名额（全局共享池 + RPM 限速）。

    RPM 超限采用**软等待**（等 1 秒再继续）而非直接失败——LLM 调用对延迟不敏感，
    平滑突发优于快速失败。名额获取是**无超时**的排队。
    """
    if not await _hit_rpm(key):
        logger.info("[limit] RPM 超限，软等待 %ss | key=%s", _RPM_SOFT_WAIT_SECONDS, key)
        await asyncio.sleep(_RPM_SOFT_WAIT_SECONDS)

    async with _acquire(_LLM_SLOT_KEY, get_settings().LLM_MAX_CONCURRENCY, key):
        yield


@asynccontextmanager
async def task_slot(key: str, limit: int | None = None):
    """任务级：占用一个任务名额（按 key 分池）。

    Args:
        key: 限流分组名。同一业务的所有入口应使用**同一个 key**，
            否则会退化成几个互不相干的池子，限不住总量。
        limit: 并发上限（从 Settings 读取后传入）。
    """
    if limit is None:
        raise ValueError("task_slot 需要显式传入 limit")
    async with _acquire(key, limit, key):
        yield
```

### 1.4 两层语义对照

| 层 | 函数 | 池划分 | 额外机制 | 控制对象 |
|---|---|---|---|---|
| 调用级 | `llm_slot(key)` | **全局共享一个池**（`__llm__`），`key` 仅用于日志/RPM | RPM 软等待 | 对模型服务的瞬时压力 |
| 任务级 | `task_slot(key, limit)` | **按 key 分池** | 无 | 下游副作用（钉钉/邮件/DB 写） |

> 关键点：`llm:intent` / `llm:time_parse` / `llm:score` **不各自成池**，
> 否则 `LLM_MAX_CONCURRENCY=20` 会被拆成几个小池，失去全局意义。

## 二、周期任务失败告警

### 2.1 问题

`PeriodicTaskManager._loop` 原先每轮失败都 `logger.exception`，任务持续失败时日志会被刷；
且没有"需要人工介入"的明确信号。

### 2.2 配置

```python
PERIODIC_TASK_FAILURE_ALERT_THRESHOLD: int = Field(
    default=5, ge=1, description="连续失败多少次后告警一次（恢复前只告警一次）"
)
```

### 2.3 代码（`app/tasks/periodic_task.py`）

类属性：

```python
class PeriodicTaskManager:
    _task: Optional[asyncio.Task] = None
    _task_name: str = "周期性任务"
    _interval_setting: str = ""

    # 连续失败计数 / 告警状态（类属性，各子类独立）
    _consecutive_failures: int = 0
    _alert_sent: bool = False
```

循环（`_loop` 全文）：

```python
    @classmethod
    async def _loop(cls) -> None:
        """定时循环：先等一个周期，再反复执行 ``_run_once``。"""
        await asyncio.sleep(cls._next_delay_seconds())

        while True:
            try:
                await cls._run_once()
            except asyncio.CancelledError:
                raise
            except Exception as exc:
                cls._consecutive_failures += 1
                count = cls._consecutive_failures
                # 默认只记一行简短告警，避免日志被刷；每 10 次保留完整堆栈便于排查
                logger.warning(
                    "%s失败（连续第 %s 次）| error=%s", cls._task_name, count, exc
                )
                if count % 10 == 0:
                    logger.exception(
                        "%s已连续失败 %s 次，保留完整堆栈", cls._task_name, count
                    )

                threshold = settings.PERIODIC_TASK_FAILURE_ALERT_THRESHOLD
                if count >= threshold and not cls._alert_sent:
                    cls._alert_sent = True
                    logger.error(
                        "[告警]%s连续失败已达 %s 次（阈值 %s），需人工介入；"
                        "恢复前不再重复告警",
                        cls._task_name, count, threshold,
                    )
            else:
                if cls._consecutive_failures:
                    logger.info(
                        "%s已恢复（此前连续失败 %s 次）",
                        cls._task_name, cls._consecutive_failures,
                    )
                cls._consecutive_failures = 0
                cls._alert_sent = False

            await asyncio.sleep(cls._next_delay_seconds())
```

### 2.4 行为对照

| 情况 | 行为 |
|---|---|
| 失败 | 计数 +1，记一行**简短 warning**（含 error 摘要） |
| 每失败 10 次 | 额外记一次完整堆栈，保留排查线索 |
| 达到阈值（默认 5）且未告警过 | 记一次 `ERROR` 告警，**恢复前不重复** |
| 成功 | 计数清零；若此前有失败，记一条"已恢复"info |

## 三、周期任务调度时刻

### 3.1 需求

- **生产模式**：每天 08:00、12:00、17:00、24:00 各执行一次；
- **开发模式**：每 15 秒执行一次。

### 3.2 配置

```python
    default="08:00,12:00,17:00,24:00",
    description="每日执行时刻（逗号分隔，24:00 表示次日 0 点）",
```

### 3.3 代码（`app/tasks/periodic_task.py`）

时刻计算：

```python
def seconds_until_next_daily_time(spec: str) -> float:
    """计算距离下一个每日执行时刻还有多少秒。

    Args:
        spec: 形如 ``"08:00,12:00,17:00,24:00"``；``24:00`` 视为次日 00:00。

    Returns:
        距下一个时刻的秒数（恒为正数）。
    """
    now = now_beijing()
    candidates = []
    for part in spec.split(","):
        part = part.strip()
        if not part:
            continue
        hour_s, minute_s = part.split(":")
        hour, minute = int(hour_s), int(minute_s)
        if hour >= 24:
            # 24:00 = 次日 00:00
            base = now.replace(hour=0, minute=0, second=0, microsecond=0) + timedelta(days=1)
        else:
            base = now.replace(hour=hour, minute=minute, second=0, microsecond=0)
        if base <= now:
            base += timedelta(days=1)
        candidates.append(base)

    if not candidates:
        raise ValueError(f"每日执行时刻配置解析为空: {spec!r}")
    return (min(candidates) - now).total_seconds()
```

模式选择：

```python
    @classmethod
    def _get_interval_minutes(cls) -> int:
        """从 Settings 读取间隔（分钟），``interval`` 模式使用。"""
        if not cls._interval_setting:
            raise NotImplementedError(f"{cls.__name__} 未设置 _interval_setting")
        return int(getattr(settings, cls._interval_setting))

    @classmethod
    def _next_delay_seconds(cls) -> float:
        """计算下一次执行的等待秒数。"""
        mode = str(settings.PERIODIC_TASK_SCHEDULING).lower()
        if mode == "interval":
            return cls._get_interval_minutes() * 60
        if mode == "daily_times":
            return seconds_until_next_daily_time(settings.PERIODIC_TASK_DAILY_TIMES)
        # auto：生产按每日时刻，其余环境按开发间隔
        if str(settings.environment).lower() == "production":
            return seconds_until_next_daily_time(settings.PERIODIC_TASK_DAILY_TIMES)
        return float(settings.PERIODIC_TASK_DEV_INTERVAL_SECONDS)
```

### 3.4 模式说明与影响

| 模式 | 行为 |
|---|---|
| `auto`（默认） | `environment == "production"` → 按每日时刻；其余 → 每 15s |
| `interval` | 强制使用子类的 `_interval_setting`（分钟），保留旧行为 |
| `daily_times` | 强制按每日时刻，不论环境 |

- `TimeoutSweepManager`（邮件回复超时）：由每 15 分钟改为**每天 4 次**（超时窗口 48h，够用）；
- `MailSubmissionSweepManager`（待确认投递超期）：同上。

回退：`PERIODIC_TASK_SCHEDULING=interval`。

## 四、任务级限流接入点

任务级与调用级同模块（`app/core/limiters.py`），函数为 `task_slot(key, limit)`。

### 4.1 为什么调用级不够

`create_agent` 是 **ReAct 循环**，一次任务内部有 3~10 次 LLM 往返。若只按单次调用限流，
一个 Agent 会同时占用多个 LLM 名额，`LLM_MAX_CONCURRENCY` 的实际效果被稀释，
也无法回答"同时在跑几个候选人的招聘流程"。

```python
        # 后台富化：独立小配额，避免抢占主流程的 LLM 并发
        async with task_slot("mail_enrich", settings.MAIL_ENRICH_MAX_CONCURRENCY):
            ...   # OCR + LLM 解析（原逻辑）
```

### 4.4 两层约束关系与注意事项

`recruit(12) + resume_parse(8) + mail_enrich(2)` 可能同时争用 `LLM(20)` 名额，
因此**调用级是 LLM 压力的最终边界，任务级是副作用的边界**。

1. **同一 key**：4 个招聘流程入口必须共用 `recruit`；
2. **禁止嵌套同 key**：图节点内部只使用 `llm_slot`，不得再 acquire `recruit`，否则死锁；
3. **不阻塞邮件轮询**：`sem.acquire()` 是 `await`，会让出事件循环；
4. **仅单 worker 有效**：改多 worker 需换 Redis 信号量；
5. **限流不等于幂等**：重复消费/重复触发仍需业务侧幂等保护。

## 五、被限流拦住时发生什么

两层都是 `await sem.acquire()` —— **排队等待（背压），不丢弃、不报错、无超时**。

| 层 | 触发 | 行为 |
|---|---|---|
| 调用级 · 并发 | 在飞 LLM 达 20 | 挂起排队，直到有名额释放 |
| 调用级 · RPM | 本分钟第 601 次 | 软等待 1s 后继续（**不重新校验**，是降速器不是硬上限） |
| 任务级 | 任务数达上限 | 挂起排队 |

后果：延迟累积（耗时 = 排队 + 执行）；HTTP 可能撞 `gunicorn timeout=60s`（但后台任务仍会执行完）；
`BackgroundTasks` / `create_task` 堆积；用户可能重复提交。

观测日志：

| 日志 | 含义 |
|---|---|
| `[limit] 等待 Xs 才拿到名额 \| key=llm:intent \| limit=20` | 调用级排了多久 |
| `[limit] 等待 Xs 才拿到名额 \| key=recruit \| limit=12` | 任务级排了多久 |
| `[limit] RPM 超限，软等待 1s` | 速率层触发 |
