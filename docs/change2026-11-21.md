## 二、P1-3：分布统计按用户可见范围收敛

### 问题

`GET /candidate/distribution` 只依赖 `get_current_user`，聚合查询没有任何部门/创建者过滤：

```python
@router.get("/candidate/distribution")
async def get_candidate_distribution(session, _: UserModel = Depends(get_current_user)):
    return await candidate_distribution_ser(session)   # 全表聚合
```

列表、下载、改状态、删除、AI 评分五处都已统一走 `CandidateRepo.get_for_user`，
唯独看板接口漏了——任意登录用户（包括普通员工）都能读到全公司候选人的
学历 / 状态 / 职位分布。

### 改动

**`app/repository/resume_repo.py`**

```python
async def distribution_rows(self, current_user: UserModel):
    stmt = (
        select(CandidateModel.status, CandidateModel.education_experience, PositionModel.title)
        .join(PositionModel, CandidateModel.position_id == PositionModel.id)
    )
    # 复用列表的可见性条件（这里已自行 join 了 positions，只取 where 部分）
    visibility = await self._visible_stmt(current_user)
    if visibility.whereclause is not None:
        stmt = stmt.where(visibility.whereclause)
    return list((await self.session.execute(stmt)).all())
```

复用 `_visible_stmt` 而不是另写一套规则，保证：
- 超管：全量
- HR：仅自己负责部门的职位
- 其他员工：仅自己创建的职位

**`app/service/candidate_ser.py`**：`candidate_distribution_ser(session, current_user)` 透传。
**`app/routers/candidate_router.py`**：路由把 `current_user` 传下去。

## 三、P1-4：时间解析的异常分类

### 问题

```python
try:
    pt = await _extract_time_from_reply(state, reply)
except Exception:
    return await can_not_find_available_time(state)   # 消耗一轮协商
```

LLM 超时 / 限流 / 网络抖动会被当成「候选人没给出有效时间」，`negotiation_round += 1`。
连续 3 次模型故障 → 候选人被永久判成「协商超时」。这与项目整体约定
（基础设施异常 → `PROCESSING_ERROR`，可人工重试）相互矛盾。

### 改动

**`_extract_time_from_reply`**：把模型调用失败统一包成 `LLMServiceError`。

```python
try:
    async with llm_slot("llm:time_parse"):
        result: ProposedTime = await llm.ainvoke(messages)
except Exception as e:
    raise LLMServiceError(f"解析候选人时间失败: {e}") from e
```

**节点内**：只把 `NegotiationError`（模型能跑、但回复无法映射成结构化时间）当作业务失败。

```python
except NegotiationError as e:
    return await can_not_find_available_time(state)
```

`LLMServiceError` 向上抛 → `node_error_wrapper` 透传 → 外层标记 `PROCESSING_ERROR`，
HR 可在后台重试，不再静默消耗协商轮次。

## 五、P2-2：校验职位；简历改为可选

### 问题

1. `create_candidate_ser` 直接把 `position_id` / `resume_id` 落库：职位不存在 → 外键违约 500；
   职位存在但当前用户无权访问 → 越权创建候选人。
2. `resume_id` 在 schema 与数据库里都是必填，但**线下投递 / 手工录入的候选人本来就没有电子简历**，
   接口却只能靠外键报错来拒绝。

### 改动

**1）创建前校验职位（存在 + 可见）**

```python
position = await PositionRepo(session).get_by_id(candidate_data.position_id)
if position is None:
    raise HTTPException(400, f"职位不存在: {candidate_data.position_id}")
_ensure_position_visible(position, current_user)
```

`_ensure_position_visible` 与列表可见性同口径：超管全量 / HR 看负责部门 / 其他人看自己创建的职位。

**2）简历可选**

| 位置 | 改动 |
|------|------|
| `CandidateCreateSchema.resume_id` | `str` → `str \| None = None` |
| `CandidateModel.resume_id` | `nullable=True` |
| `CandidateSchema.resume` | `ResumeSchema` → `ResumeSchema \| None` |
| 迁移 `f2b3c4d5e6a7` | `ALTER TABLE candidates ALTER COLUMN resume_id DROP NOT NULL` |

语义：
- **不传** `resume_id` → 允许，候选人不带简历（线下投递场景）；
- **传了** → 必须真实存在，否则 400（而不是外键违约 500）。

`ix_candidates_resume_id` 仍是唯一索引；PostgreSQL 唯一索引允许多个 NULL，
「一份简历只挂一个候选人」的约束不变。

> 前端注意：`CandidateSchema.resume` 现在可能为 `null`，展示处需判空。

## 八、P2-5：复核记录原子抢占

### 问题

`resolve_review` 的流程是「读记录 → 校验 PENDING（事务 1）→ 执行动作（无事务）→ 落结果（事务 2）」，
两个 HR 同时点「执行」都会通过 PENDING 校验，导致**重复执行同一动作**
（可能重复恢复状态图、重复建投递记录）。

### 改动

**`MailReviewRepo` 新增租约式抢占**（不改 `status`，避免新增枚举与迁移）：

```python
async def claim(self, review_id, *, resolver_id, lease_seconds) -> bool:
    """条件更新：claimed_at 为空或租约过期才可抢。"""
    result = await self.session.execute(
        update(MailReviewModel).where(
            MailReviewModel.id == review_id,
            MailReviewModel.status == MailReviewStatusEnum.PENDING,
            or_(
                MailReviewModel.claimed_at.is_(None),
                MailReviewModel.claimed_at < now - timedelta(seconds=lease_seconds),
            ),
        ).values(resolver_id=resolver_id, claimed_at=now)
        .execution_options(synchronize_session=False)
    )
    return result.rowcount > 0
```

租约由 `Settings.MAIL_REVIEW_CLAIM_LEASE_SECONDS` 给出（默认 300 秒），
并与动作硬超时联动校验（见第十三节）。

新增 `release_claim()`：动作失败时清空 `resolver_id` + `claimed_at`，
让本人/他人可以立刻重试，而不是等租约自然过期。

**`resolve_review`** 在同一个事务里完成「校验 + 抢占」，抢不到直接报错：

```
ValueError: 该记录正在被其他人处理，请刷新后重试
```

动作执行失败时释放租约后再抛，保持记录仍是 PENDING（不会「标记已处理但其实没做」）。

进程崩溃留下的租约会在 `lease_seconds` 后自动可被重新抢占，不会永久锁死。

### 为什么是 `claimed_at` 而不是复用 `resolved_at`

初版把 `resolved_at` 借来当租约起点，语义是错的：

| 列 | 含义 | 写入时机 |
|----|------|----------|
| `claimed_at`（新增） | **认领时间**——谁在什么时候开始处理 | 抢占到时写入；动作失败清空；完成后保留作历史 |
| `resolved_at`（原有） | **处理完成时间** | 只在最终 resolve 时写入 |

`resolved_at` 已经通过 `GET /mail-review/{id}` 暴露给前端（`mail_review_api.ts`），
把「执行中」写成 `resolved_at` 会让列表显示成「已完成」，且丢失真正的完成时间。
因此拆成两列，接口同步增加 `claimed_at` 字段（前端类型里是可选字段，向后兼容）。

## 十一、租约与超时收敛（追加）

评审提出的问题：**认领租约 10 分钟是否过长？**

结论：**偏长，但直接调小会引入更严重的问题**。租约真正保护的不是正常路径
（处理完成即把 `status` 改成 RESOLVED，租约立即失效），而是**进程被硬杀后、
记录最晚多久能被别人接手**。因此它必须与「动作耗时上界」绑定，而当时这个上界并不存在。

### 11.1 问题：动作耗时无上界

| 环节 | 改前约束 |
|------|----------|
| `task_slot("recruit")` 排队 | 无上限 |
| `llm_slot` 排队 | 无上限 |
| `check_availability` 的 LLM 调用 | **无超时**（`ChatOpenAI` 未显式配置） |
| `scoring` 的 LLM 调用 | **无超时** |
| 钉钉 HTTP | 30s |

最坏情况下动作可能超过 10 分钟，租约 600s 既非「过长」也非「安全」，只是没有依据。

### 11.2 改动

| 改动 | 说明 |
|------|------|
| 新增 `MAIL_REVIEW_EXECUTE_TIMEOUT_SECONDS`（默认 180s） | `execute_intent` 外包一层 `asyncio.wait_for`，超时后释放租约并抛 `TimeoutError` |
| 新增 `MAIL_REVIEW_CLAIM_LEASE_SECONDS`（默认 300s） | 租约改为配置项，**由启动期校验保证 > 动作硬超时** |
| `ignore` 不占用租约 | 无副作用且幂等，直接落状态 |
| 新增 `LLM_CALL_TIMEOUT_SECONDS`（默认 60s） | 给 `check_availability` 与 `scoring` 的 LLM 调用补硬超时 |

```python
# app/core/config.py —— 启动即校验，避免线上偶发重放
@model_validator(mode="after")
def _validate_review_lease(self) -> "Settings":
    if self.MAIL_REVIEW_CLAIM_LEASE_SECONDS <= self.MAIL_REVIEW_EXECUTE_TIMEOUT_SECONDS:
        raise ValueError("MAIL_REVIEW_CLAIM_LEASE_SECONDS 必须大于 MAIL_REVIEW_EXECUTE_TIMEOUT_SECONDS")
    return self
```

```python
# app/service/mail_review_ser.py
if not await repo.claim(
    review_id,
    resolver_id=resolver_id,
    lease_seconds=settings.MAIL_REVIEW_CLAIM_LEASE_SECONDS,
):
    raise ValueError("该记录正在被其他人处理，请刷新后重试")

try:
    await asyncio.wait_for(
        execute_intent(email, parsed_intent),
        timeout=settings.MAIL_REVIEW_EXECUTE_TIMEOUT_SECONDS,
    )
except Exception as exc:
    await ...release_claim(...)          # 立刻可被重试
    if isinstance(exc, TimeoutError):
        raise TimeoutError("复核动作执行超时（180s），记录已释放，请稍后重试")
    raise
```

路由层把 `TimeoutError` 映射为 **504**（`ValueError` 仍为 400/404）。

### 11.3 取值依据

| 值 | 取值 | 理由 |
|----|------|------|
| 动作硬超时 | 180s | 正常路径秒级；最坏要覆盖「图恢复 + 一次 LLM + 钉钉 + 发信」 |
| 租约 | 300s | = 超时 + 120s 余量，保证动作绝不会在租约内被抢走 |
| 图内 LLM 超时 | 60s | 与意图分类的 30s 同量级，留出重试与降级余量 |

相比原来的固定 600s：崩溃后的恢复等待从 **10 分钟降到 5 分钟**，
而「重复执行」的风险反而更低（因为动作本身有了 180s 上界）。

### 11.4 新增配置项

| 环境变量 | 默认值 | 说明 |
|----------|--------|------|
| `MAIL_REVIEW_EXECUTE_TIMEOUT_SECONDS` | 180 | 复核动作硬超时 |
| `MAIL_REVIEW_CLAIM_LEASE_SECONDS` | 300 | 认领租约（须大于上者，启动期校验） |
| `LLM_CALL_TIMEOUT_SECONDS` | 60 | 图内 LLM 调用超时 |

### 11.5 未做：心跳续租

按 LangGraph step 回调续租可以进一步缩短租约，但需要侵入图执行流程；
在当前「180s 超时 + 300s 租约」下收益有限，暂不引入。
