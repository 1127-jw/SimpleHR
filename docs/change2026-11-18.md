# 变更记录 2026-11-18

本次主题：**全仓库缺陷排查与修复**（17 项），外加三处后台任务调度相关的整理
（日志标识统一 → 调度参数按需取值 → 调度模式简化）。
缺陷的完整记录见根目录 **`11-18-bug.md`**（§1–§11）。

不靠印象：先跑客观检查（AST 模式扫描 / 全模块导入 / 路由去重 / 前后端路径契约比对），
再逐条人工复核。共定位 **3 个高危、6 个中等、8 个低危**，全部修复并补回归测试。

1. **「上午/下午/全天」提议被排到凌晨零点**——提示词规定这类回复的 `proposed_time`
   一律填**当日 00:00:00**（只用于携带日期），节点却把这个 00:00 直接写进
   `proposed_interview_time` → 日程建在 00:00–01:00，确认邮件写「00:00」。
   新增 `resolve_interview_slot()`，从窗口内的空闲段反推真实起点。详见 §二·①；
2. **「7 天内无空档」后回「确认」→ `KeyError`**：该分支没确定任何时间，
   确认分支却直接放行，`confirm_node` 读 `state["proposed_interview_time"]` 崩溃。详见 §二·②；
3. **`GET /candidate/ai-score/{id}` 越权**：同文件其余接口都走 `get_for_user`，
   唯独它按 id 直取，任何登录用户可读他人 AI 评分。详见 §二·③；
4. **协商全程静默**：提议时间被拒、轮次耗尽、48h 超时都不发信——
   候选人以为约成了，系统在等一封不会来的邮件。详见 §三·①；
5. **钉钉日程解析两处脆弱**：`events` 缺字段返回 `None`（下游 `for` 直接
   `TypeError`）、全天日程只有 `date` 没有 `dateTime`（`KeyError`）。详见 §三·②；
6. **超时巡检锁会误删他人锁**：`finally` 无条件 `DEL`，本轮超过 TTL 且锁已被
   别的 worker 抢走时会删掉别人的锁 → 并发巡检、重复 resume。详见 §三·③；
7. **`confirm_node` 先落库后调外部系统**：钉钉失败时库已 commit，
   留下「待面试但无日程、无邮件」的脏状态。详见 §三·④；
8. **投递列表无分页、`status` 不校验**。详见 §三·⑤；
9. **低危 8 项**：`raise str`、裸 `except:`、docstring `\Seen` 警告、
   `str(None)` 当 refresh_token、限流 `limit<=0` 语义相反、改密不吊销会话、
   简历 Content-Type 硬编码、4 个文件带 BOM。详见 §四；
10. **后台任务日志标识统一**：`_log_name()` 输出 `类名:任务名`，8 处日志一次改齐。详见 §五；
11. **调度参数按需取值**：`_get_interval_minutes()` 原本在**传参位置**求值，
    三种模式都会读间隔配置——而生产默认 `daily_times` 根本用不到它，
    配置一坏就整条任务带崩。改为按需取值。详见 §八（该 `interval` 档已在 §九 移除）；
12. **调度模式简化**：周期巡检不再三选一，由 `Settings.PERIODIC_TASK_MODE`
    按 `DEBUG` 推导（debug → 15 秒一轮，生产 → 每日时刻）；邮件轮询改为独立开关
    `MAIL_POLL_INTERVAL_SECONDS`（默认 15 秒），不看 `DEBUG`、不跟随全局。
    随之删掉 `PERIODIC_TASK_SCHEDULING` / `MAIL_POLL_SCHEDULING` /
    `MAIL_POLL_INTERVAL_MINUTES` / 两个 `*_SWEEP_INTERVAL_MINUTES`，
    以及 `_interval_setting` / `resolve_mode` / `resolve_following`。详见 §九；
13. **中断节点日志去冗**：挂起前那两条日志（其中一条文案写成「恢复线程」）合成一条，
    `thread_id` 挪到真正发出 `Command(resume=...)` 的恢复侧。详见 §十；
14. **接口禁用浏览器缓存**：新增 `no-store` 中间件——此前接口只发
    `content-length` / `content-type`，浏览器会启发式缓存 `GET 200`，
    DevTools 显示 `200 OK (from disk cache)`，请求根本没到服务器。详见 §十一；
15. **`get_redis` 漏 await（线上事故）**：它是 `async def` 但只是取模块级单例、
    没有任何 I/O，三处调用方没写 `await` → `r` 成了 coroutine →
    `'coroutine' object has no attribute 'set'`，超时巡检连续失败 30 轮。
    改为**同步 getter**，并补 3 条契约测试。详见 §十二；
16. **`MailPollTimer` 并入 `PeriodicTaskManager`**：此前它丢掉 `run_with_retry`
    的返回值，失败从不计数、从不告警（`MailManager._poll_once` 还额外吞异常，
    等于双重屏蔽）。并入后走统一的 `_on_failure` / `[bg_task_alert]` 通路。详见 §十三；
17. **日程接口 + 数据总览改版**：把 `dingtalk_ser` 的取日程能力包成
    `GET /calendar/events`（当前用户未来 N 天）；首页上排从「整宽趋势图」改为
    「近 7 天趋势 2/3 + 我的日程 1/3」。详见 §十四；

**一个值得记下的教训**：AST 扫描报出「`check_am_or_pm` 不校验提议时间是否落在
空闲区间」，我据此写了可执行复现，看起来证据确凿。**但归因是错的**——查
`PROPOSED_TIME_SYSTEM_PROMPT` 第 3.2 节才确认：对「上午/下午/全天」三类回复，
提示词明确规定 `proposed_time` 填**当日 00:00:00**，它只是携带日期的载体。
谓词函数忽略时分是对的。真正的问题在下游：节点把这个 00:00 当成了面试时间。

症状观察正确、病灶定位错误——所以「能复现」不等于「归因正确」，
复现只证明现象存在，不证明你找的那行代码是原因。

（附带一提：扫描器最初把 `.uv-python/`、`.uv-cache/` 一起扫了，输出被标准库
淹没；也没有跳过 BOM，`ast.parse` 直接对 4 个文件报 `invalid non-printable
character U+FEFF`。这两个都是工具问题，不是项目问题——修正扫描范围后才有意义。）

## 二、高危三项

### ① 模糊提议被排到凌晨零点

`resolve_interview_slot(strategy, slots, proposed_dt, duration, window)` 把
「够不够」升级为「用哪一段」：

```python
if strategy_name == "hours":
    for start, end in available_slots:
        if start <= proposed_dt and proposed_dt + duration <= end:
            return proposed_dt          # 准确时间原样用
    return None
if strategy_name == "all":
    for start, end in available_slots:
        if end - start >= duration:
            return start                # 取空闲段起点
    return None
# am / pm：窗口内第一段够长的空闲段的起点
```

原有测试没兜住，是因为 `test_am_pm_window_compare_is_timezone_safe` 只测了
`check_am_or_pm` 的**时区安全**（boolean），没测节点输出的**具体时间**。

### ② 「7 天内无空档」后回「确认」→ `KeyError`

`email_invite` 无空档分支只发「能否改到 7 天后」的通知，没确定时间；
`check_availability` 的 `pt.confirm` 分支却直接放行到 confirm。
加状态守卫回到协商，`confirm_node` 同时把裸 `KeyError` 换成
`InterviewSchedulingError`（`BusinessException`，会带可读消息进错误状态）。

### ③ `GET /candidate/ai-score/{id}` 越权

同文件列表 / 下载 / 改状态 / 删除**全部**走 `get_for_user`，只有它按 id 直取。
补上同一套可见性判定与同一句 404 文案（避免用状态码差异枚举 id）。

## 四、低危八项

`raise result`（抛字符串会变 `TypeError`）、裸 `except:`、docstring `\Seen`
的 `SyntaxWarning`、`str(None)` 当 refresh_token（见 §三·⑥）、
限流 `limit<=0` 语义与 `limiters.py` 相反（前者全拒、后者不限）、
改密不吊销会话、简历 Content-Type 硬编码 `application/pdf`、4 个文件带 BOM。

其中**改密吊销**用「会话纪元」而非 jti 集合索引：只多一个键
`pwd_reset_at:{email}`，token 带 `iat`，早于纪元的一律拒绝兑换。
`iat` 刻意用带小数的 `timestamp()`——整秒精度下「同一秒内先发 token 后改密」
与「先改密后登录」不可能同时判对。

## 五、后台任务日志标识统一

`PeriodicTaskManager` 新增 `_log_name()` 返回 `f"{cls.__name__}:{cls._task_name}"`，
替换**全部 8 处**任务名日志（`init` / `close` / `_on_retry` / `_on_success` /
`_on_failure`）。

要点是**一次改齐**：只改 `init` 两处时，同一任务会同时出现
`TimeoutSweepManager_邮件回复超时巡检已初始化`、`邮件回复超时巡检已停止`、
`邮件回复超时巡检执行失败` 三种口径，半改比不改更糟。

`asyncio.create_task(..., name=cls._task_name)` 刻意保持短名——那是任务对象标识，
出现在 `asyncio.all_tasks()` / 卡死诊断里，与日志口径是两件事。
`[bg_task_alert]` 前缀仍在消息开头，告警规则按它锚定，不受影响。

## 八、追加：调度参数按需取值

复查 `_get_interval_minutes()` 时发现的一处耦合缺陷。

### 8.1 现象

```python
interval_seconds=cls._get_interval_minutes() * 60,   # ← 写在传参位置
```

`delay_seconds` 只在 `MODE_INTERVAL` 分支读 `interval_seconds`，`dev_interval`
与 `daily_times` 模式直接丢弃。但 Python 实参先求值，**三种模式都会读**。
实测（把 `_get_interval_minutes` 换成必定抛错的替身）：

```
dev_interval -> 调用了 _get_interval_minutes
interval     -> 调用了 _get_interval_minutes
daily_times  -> 调用了 _get_interval_minutes
```

### 8.2 为什么这是缺陷而不是风格问题

生产默认 `PERIODIC_TASK_SCHEDULING=auto` → 生产环境解析成 **`daily_times`**。
也就是说：**一个当前模式根本用不到的配置项，缺了、改名了、类型坏了，
就能让生产起不来**——而它本来与此无关。`_max_interval_seconds` 里是同一处调用，
心跳指标同理。

### 8.3 修法

`scheduler.delay_seconds` / `max_interval_seconds` 把 `interval_seconds`、
`daily_times` 改成可选，模式缺了自己那份参数就显式 `ValueError`（不再静默算错）；
两个调用方（`PeriodicTaskManager` 与 `MailPollTimer`）改成按需取值：

```python
mode = cls._resolve_mode()
return scheduler.delay_seconds(
    mode,
    dev_interval=settings.PERIODIC_TASK_DEV_INTERVAL_SECONDS,
    interval_seconds=(cls._get_interval_minutes() * 60)
                     if mode == scheduler.MODE_INTERVAL else None,
    daily_times=settings.PERIODIC_TASK_DAILY_TIMES,
)
```

改后实测：`dev_interval` → 15.0、`daily_times` → 7588（都不再读间隔配置），
`interval` → 照常读取。

### 8.4 顺带确认：`if not cls._interval_setting` 这个守卫

它**不是逻辑错误**，但只防了一半：

| 存在哪 | 是什么 | 为什么 |
|---|---|---|
| 类属性 `_interval_setting` | **键名**（字符串） | 声明「本任务的间隔由哪个配置项控制」 |
| `Settings.EMAIL_REPLY_SWEEP_INTERVAL_MINUTES` | **值** | 运维要在 `.env` 里按环境改，不改代码、不重新发版 |

对比 `_task_name` 存的是**值**（纯日志标签，没有按环境调整的需求）。
守卫的作用是：子类忘声明键名时给出 `NotImplementedError: XxxManager 未设置
_interval_setting`，而不是让 `getattr(settings, "")` 抛
`AttributeError: 'Settings' object has no attribute ''`——后者看起来像 Settings 的 bug。

但它只检查「键名非空」，**不检查键名真的存在于 `Settings`**：拼错一个字母
（`..._MINUTE`）守卫照样通过，`getattr` 抛 `AttributeError`。
两个子类目前都设了，所以它是给未来子类的保险（眼下是死代码）。
本轮**未改**，留作可选加固：把守卫升级成 `hasattr` 校验即可。

> **后续（§九）**：`interval` 档已从周期巡检里彻底移除，`_interval_setting` /
> `_get_interval_minutes` 一并删除，本节的守卫讨论随之成为历史。

## 十、追加：中断节点日志去冗

`get_candidate_email_reply_node` 原本在**一次挂起之前**连打两条日志：

```python
logger.info("[email_reply] waiting for candidate reply | candidate_id=%s", cid)
logger.info(
    "[email_reply] resume thread before interrupt | candidate_id=%s | thread_id=%s",
    cid, state["candidate"].email,
)
reply = interrupt("candidate_email_reply")
```

第二条**文案与事实相反**：此刻什么都没恢复，下一行就是 `interrupt()`。
真正的恢复发生在 `notify._resume_candidate_graph()`（邮件触发）与
`timeout_tasks.sweep_stale_email_replies()`（48h 超时触发），那两处才该打 `thread_id`。

其余两个问题：

- 两行同一时刻，信息重叠——第二条只多一个 `thread_id`；
- 该节点每轮协商都会重入（`check_availability → get_candidate_email_reply_node` 循环），
  一个候选人协商 3 轮就刷 6 行，而 `thread_id` 是恒定值（`candidate.email`）。

`resume thread before interrupt` 这个说法像是早期实现的残留——那时节点可能真的
自己恢复线程，改成 `interrupt()` 之后日志没跟着改。

**改后**：

| 位置 | 日志 |
|---|---|
| `check_availability_node.py` | `[email_reply] 挂起，等待候选人回复 \| candidate_id=… \| thread_id=…`（只留一条） |
| `notify.py` | `[notify] 恢复招聘图 \| candidate_id=… \| thread_id=…`（发 `Command(resume=…)` 之前） |
| `timeout_tasks.py` | `[timeout_sweep] 恢复超时的招聘图 \| candidate_id=… \| thread_id=…` |

`thread_id` 的价值在于把「挂起在哪个节点」与「被哪次 resume 唤醒」对上；
放在挂起处只能看到一半，放在恢复处才闭环。失败路径原本就带 `thread_id`，
这次把成功路径补齐。

## 十一、追加：接口禁用浏览器缓存

### 11.1 现象

DevTools 里 `GET /position/list` 显示 **`200 OK (从磁盘缓存)`**——请求**没有发到服务器**，
浏览器直接用了本地 HTTP 缓存里的副本（Size 列显示 from disk cache，Timing 里也没有真实传输耗时）。

### 11.2 为什么会被缓存

浏览器命中缓存要同时满足两条：

1. **响应可缓存**：`GET` + `200` 默认就可缓存；
2. **还在新鲜期内**：靠 `Cache-Control: max-age` / `Expires`，
   没有显式新鲜度信息时由浏览器按启发式策略决定。

实测本项目接口此前发出的头只有：

```
content-length / content-type
```

（`grep` 全仓 `Cache-Control|Expires|ETag|Last-Modified` 零命中；
`JSONResponse.raw_headers` 实测也只有这两项。）
没有任何缓存指令，等于把决定权完全交给浏览器——本地开发期、重复刷新、
重复导航时就容易命中。

### 11.3 修法

新增 [app/middleware/cache_control_middleware.py](app/middleware/cache_control_middleware.py)，
给所有响应加 `Cache-Control: no-store`：

| 指令 | 行为 |
|---|---|
| `no-store` | 任何缓存都不得存储，每次必发请求。**动态接口用这个** |
| `no-cache` | 仍可存储，但每次必须 revalidate（仍会发请求，可能 304） |

注册在 `setup_middlewares()` 里（CORS 之后、请求 ID 之前）——它只改写响应头，
与中间件顺序无关。

> 注意：真正的静态资源不要加这个头。本项目已移除 `/media` 静态挂载，
> 当前没有需要放过的静态路由。

### 11.4 验证

真实应用（`create_app()` + `TestClient`）：

```
/                -> 200  Cache-Control=no-store
/openapi.json    -> 200  Cache-Control=no-store
```

`tests/test_cache_control.py` 3 条：中间件本身、**注册入口确实接上**
（只测中间件的话，漏注册不会被发现）、POST 同样生效。

## 十二、追加：`get_redis` 漏 await（线上事故）

### 12.1 现象

线上日志：

```
WARNING | TimeoutSweepManager:邮件回复超时巡检执行失败（重试耗尽，连续第 30 次）| error='coroutine' object has no attribute 'set'
ERROR   | TimeoutSweepManager:邮件回复超时巡检已连续失败 30 次，保留完整堆栈
```

### 12.2 根因

`get_redis()` 写成了 `async def`，但它只是取模块级单例，**没有任何 I/O**。
三处调用方没写 `await`，`r` 成了 coroutine：

| 位置 | 代码 |
|---|---|
| `app/tasks/timeout_tasks.py` | `r = get_redis()` → `await r.set(...)` ← 就是日志这条 |
| `utils/emailbot/bot.py` | `r = get_redis()` → `await r.hset(...)` |
| `app/core/limiters.py` | `await hit(get_redis(), ...)` → 内部 `r.eval(...)` |

另有两处**写了** `await`（`agents/candidate.py`、`service/dingtalk_ser.py`）。
也就是说同一个函数，5 个直接调用点里 2 个 await、3 个不 await——
**无论把它定义成 sync 还是 async，都有一半调用点是错的**。

### 12.3 修法

把 getter 改成**同步**，与 `get_http_client()` / `get_checkpointer()` /
`get_settings()` 的写法一致，再去掉那两处多余的 `await`：

```python
def get_redis() -> redis.Redis:
    if redis_client is None:
        raise RuntimeError("Redis 未初始化")
    return redis_client
```

`Depends(get_redis)` 在 10 个路由里使用，FastAPI 对同步依赖会自动放线程池，不受影响。

### 12.4 为什么旧测试没拦住

`tests/test_bugfixes_1117.py` 把 `timeout_tasks.get_redis` monkeypatch 成了
**sync lambda**——正好掩盖了生产里的 `async` 定义。
**测试替身与真实契约不一致**，是这类 bug 能溜过去的原因。

### 12.5 验证

- 复现：把 `get_redis` 换回 `async def`，`sweep_stale_email_replies()` 立刻抛
  `AttributeError: 'coroutine' object has no attribute 'set'`，与线上日志逐字一致。
- `tests/test_redis_getter.py` 3 条：getter 必须同步、`Depends` 路径仍可用、
  **用真实 getter** 跑通巡检（不再用 sync lambda 替身）。

## 十三、`MailPollTimer` 并入 `PeriodicTaskManager`

### 13.1 收益

`MailPollTimer` 原本把 `run_with_retry` 的返回值**丢掉**——失败从不计数、
