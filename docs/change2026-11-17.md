## 一、问题：固定阈值在 `daily_times` 下永久误报

### 1.1 现象

`PeriodicTaskManager._next_delay_seconds()` 在 `auto` 模式下，**生产环境按
`PERIODIC_TASK_DAILY_TIMES` 执行**（默认 `08:00,12:00,17:00,24:00`），
一天只跑 4 次。而旧方案的心跳判定是：

```python
# 旧方案（错误）
_BG_MAX_SILENCE_SECONDS = 300.0        # 固定 5 分钟
metric.add_metric([job], 1.0 if now - ts < _BG_MAX_SILENCE_SECONDS else 0.0)
```

```text
TimeoutSweepManager 每 8 小时才执行一次
  → 300 秒后心跳必然过期
  → simplejob_bg_task_alive 几乎恒为 0
  → MailBotDead / SweepDead 永久误报 → 三天后必被静默，比没有还糟
```

### 1.2 第二个坑：心跳查不出「任务失败」

`PeriodicTaskManager._loop()` 里 `_run_once()` 抛异常被 `except` 吞掉后**继续循环**：

```python
# app/tasks/periodic_task.py
while True:
    try:
        await cls._run_once()
    except asyncio.CancelledError:
        raise
    except Exception as exc:
        cls._consecutive_failures += 1     # ← 失败被吞，循环继续
        ...
    await asyncio.sleep(cls._next_delay_seconds())
```

所以「循环还在跑、但任务一直失败」时心跳照常刷新，**心跳无法区分「停了」和「在失败」**。

### 1.3 修正后的判据

```text
存活判据：time() - last_run > expected_interval × 3
失败判据：consecutive_failures > 0
```

- 阈值由调度配置推导（`expected_interval`），**不写死**；
- `last_run` 只在**成功**时刷新；
- 连续失败次数单独暴露成指标。

## 二、新增 `app/tasks/scheduler.py`

调度策略集中在一处，只提供**纯函数**（不读配置、无副作用），便于单测。

```python
"""后台任务的调度策略。

三种生效模式：

* ``dev_interval``：开发/调试，固定短间隔
* ``interval``：固定间隔（秒）
* ``daily_times``：每日指定时刻
"""
from __future__ import annotations

from datetime import datetime, timedelta

from utils.time_ISO8601_datatime import now_beijing

MODE_DEV = "dev_interval"
MODE_INTERVAL = "interval"
MODE_DAILY = "daily_times"

_DAY_SECONDS = 24 * 3600


def resolve_mode(scheduling: str, *, is_production: bool) -> str:
    """``auto``（默认）：生产环境 → ``daily_times``，其余环境 → ``dev_interval``。

    Raises:
        ValueError: 配置值不是 ``auto`` / ``interval`` / ``daily_times``。
    """
    raw = (scheduling or "auto").strip().lower()
    if raw == "auto":
        return MODE_DAILY if is_production else MODE_DEV
    if raw not in (MODE_INTERVAL, MODE_DAILY):
        raise ValueError(
            f"未知的调度模式: {scheduling!r}（可选：auto / interval / daily_times）"
        )
    return raw


def resolve_following(
    own_scheduling: str,
    global_scheduling: str,
    *,
    is_production: bool,
) -> str:
    """解析「默认跟随全局」的子任务调度模式。

        全局=auto(生产) + 邮件=auto      → daily_times
        全局=auto(生产) + 邮件=interval  → interval    ← 巡检按时刻，邮件高频
        全局=interval   + 邮件=auto      → interval
    """
    raw = (own_scheduling or "auto").strip().lower()
    effective = global_scheduling if raw == "auto" else raw
    return resolve_mode(effective, is_production=is_production)


def parse_daily_minutes(spec: str) -> list[int]:
    """把 ``"08:00,12:00,17:00,24:00"`` 解析成「当天第几分钟」列表。

    ``24:00`` 归一化为 ``1440``（即次日 00:00），便于计算跨天间隔。
    """
    minutes: set[int] = set()
    for part in spec.split(","):
        part = part.strip()
        if not part:
            continue
        hour_s, minute_s = part.split(":")
        hour, minute = int(hour_s), int(minute_s)
        if not (0 <= minute < 60):
            raise ValueError(f"时刻分钟数非法: {part!r}")
        if hour >= 24:
            if hour != 24 or minute != 0:
                raise ValueError(f"超过 24:00 的时刻不支持: {part!r}")
            minutes.add(_DAY_SECONDS // 60)
        else:
            minutes.add(hour * 60 + minute)
    if not minutes:
        raise ValueError(f"每日执行时刻配置解析为空: {spec!r}")
    return sorted(minutes)


def seconds_until_next_daily_time(spec: str, *, now: datetime | None = None) -> float:
    """计算距离下一个每日执行时刻还有多少秒（恒为正数）。"""
    now = now or now_beijing()
    today = now.replace(hour=0, minute=0, second=0, microsecond=0)
    candidates = []
    for m in parse_daily_minutes(spec):
        base = today + timedelta(minutes=m)
        if base <= now:
            base += timedelta(days=1)
        candidates.append(base)
    return (min(candidates) - now).total_seconds()


def daily_max_gap_seconds(spec: str) -> float:
    """时刻表中相邻两次执行的最大间隔（含首尾跨天），单位秒。

    只配置了一个时刻时，按 24 小时计。
    """
    minutes = parse_daily_minutes(spec)
    if len(minutes) < 2:
        return float(_DAY_SECONDS)
    gaps = [minutes[i + 1] - minutes[i] for i in range(len(minutes) - 1)]
    # 首尾跨天：最后一个时刻 → 次日第一个时刻
    gaps.append(minutes[0] + (_DAY_SECONDS // 60) - minutes[-1])
    return float(max(gaps) * 60)


def delay_seconds(mode: str, *, dev_interval: float,
                  interval_seconds: float, daily_times: str) -> float:
    """按模式计算下一次执行的等待秒数。"""
    if mode == MODE_DEV:
        return max(1.0, float(dev_interval))
    if mode == MODE_INTERVAL:
        return max(1.0, float(interval_seconds))
    return seconds_until_next_daily_time(daily_times)


def max_interval_seconds(mode: str, *, dev_interval: float,
                         interval_seconds: float, daily_times: str) -> float:
    """按模式计算「相邻两次执行的最大间隔」，用于心跳阈值推导。

    这是后台任务健康检查的关键输入：阈值必须跟调度配置联动，
    写死（例如固定 300 秒）在 ``daily_times`` 模式下会永久误报。
    """
    if mode == MODE_DEV:
        return max(1.0, float(dev_interval))
    if mode == MODE_INTERVAL:
        return max(1.0, float(interval_seconds))
    return daily_max_gap_seconds(daily_times)
```

**关键计算结果**：`08:00,12:00,17:00,24:00` 的间隔依次为
4h / 5h / 7h / **8h**（`24:00 → 次日 08:00`），`daily_max_gap_seconds()` 返回 **28800 秒**。

## 三、`PeriodicTaskManager` 重构

删除本地 `seconds_until_next_daily_time()`，改走 scheduler；新增 `_max_interval_seconds()`。

```python
# app/tasks/periodic_task.py
from app.tasks import scheduler

    @classmethod
    def _get_interval_minutes(cls) -> int:
        """从 Settings 读取间隔（分钟），``interval`` 模式使用。"""
        if not cls._interval_setting:
            raise NotImplementedError(f"{cls.__name__} 未设置 _interval_setting")
        return int(getattr(settings, cls._interval_setting))

    @classmethod
    def _resolve_mode(cls) -> str:
        """当前生效的调度模式。"""
        return scheduler.resolve_mode(
            settings.PERIODIC_TASK_SCHEDULING,
            is_production=str(settings.environment).lower() == "production",
        )

    @classmethod
    def _next_delay_seconds(cls) -> float:
        """计算下一次执行的等待秒数。"""
        return scheduler.delay_seconds(
            cls._resolve_mode(),
            dev_interval=settings.PERIODIC_TASK_DEV_INTERVAL_SECONDS,
            interval_seconds=cls._get_interval_minutes() * 60,
            daily_times=settings.PERIODIC_TASK_DAILY_TIMES,
        )

    @classmethod
    def _max_interval_seconds(cls) -> float:
        """当前模式下相邻两次执行的最大间隔，用于心跳阈值推导。

        ``daily_times`` 模式下返回时刻表中的最大间隔（含跨天），
        避免用固定阈值在生产环境产生永久误报。
        """
        return scheduler.max_interval_seconds(
            cls._resolve_mode(),
            dev_interval=settings.PERIODIC_TASK_DEV_INTERVAL_SECONDS,
            interval_seconds=cls._get_interval_minutes() * 60,
            daily_times=settings.PERIODIC_TASK_DAILY_TIMES,
        )
```

### 3.1 启动策略：首次执行不再等一整个周期

**问题**：`_loop()` 原本第一句就是 `await asyncio.sleep(cls._next_delay_seconds())`。
在 `daily_times` 模式下这个值最长是 **8 小时**——应用启动后第一次巡检要等到
下一个时刻才跑，中间完全没有心跳数据（也就会误触发 `BgTaskNotRunning`）。

**改法**：把「首次执行的等待」和「周期间的等待」拆开：

```python
# app/tasks/periodic_task.py
    @classmethod
    async def _loop(cls) -> None:
        """定时循环：启动宽限后先跑一轮，再按周期反复执行 ``_run_once``。

        * **首次执行前只等** ``BACKGROUND_TASK_STARTUP_DELAY_SECONDS``（默认 2 分钟）：
          既避免应用启动瞬间压一波数据库查询，也避免 ``daily_times`` 模式下
          首次任务要等上数小时（最长 8 小时）。
        * 之后每轮结束用 ``_next_delay_seconds()`` 计算下一次等待，
          因此每日时刻模式下会自动对齐到下一个时刻。
        """
        await asyncio.sleep(settings.BACKGROUND_TASK_STARTUP_DELAY_SECONDS)

        while True:
            try:
                await cls._run_once()
            except asyncio.CancelledError:
                raise
            except Exception as exc:
                ...        # 失败处理不变
            await asyncio.sleep(cls._next_delay_seconds())

    @classmethod
    async def init(cls) -> None:
        if cls._task is not None:
            logger.warning("%s已初始化，跳过重复 init", cls._task_name)
            return
        cls._task = asyncio.create_task(cls._loop(), name=cls._task_name)
        logger.info(
            "%s已启动：首次执行约在 %.0f 秒后，此后按 %s 模式调度",
            cls._task_name,
            settings.BACKGROUND_TASK_STARTUP_DELAY_SECONDS,
            cls._resolve_mode(),
        )
```

邮件轮询计时器有同样的问题（`interval` 模式下要等 30 分钟才首跑），
所以**同步修改**，并抽出一个便于测试的方法：


| 生产邮件 `interval` | 30 分钟后 | **2 分钟**后 |

### 3.2 失败重试与告警：重试属于「一次执行」内部

**需求**：失败后应重试；重试 3 次仍失败才报警；且结合「容忍 2 次执行失败」，
即**第 3 次执行失败才告警**。

**关键区分**：

```text
一次调度执行 = 首次尝试 + 最多 3 次重试
  ├─ 任一次成功 → 本次执行成功（计数清零）
  └─ 全部失败   → 记为「一次执行失败」，参与连续失败计数
                    └─ 连续 3 次执行失败（容忍 2 次）→ 告警
```

#### 新增 `app/tasks/retry.py`

```python
"""后台任务的失败重试。

语义：**重试属于「一次执行」内部**。只有重试全部耗尽仍失败，
才记为一次「执行失败」，进而参与连续失败计数与告警判定。

注意：``asyncio.CancelledError`` **不重试**，直接向上抛（应用关闭时不该拖延）。
"""
from __future__ import annotations

import asyncio
import logging
from typing import Awaitable, Callable, Optional

logger = logging.getLogger(__name__)

DEFAULT_BASE_DELAY_SECONDS = 1.0
DEFAULT_MAX_DELAY_SECONDS = 30.0


async def run_with_retry(
    fn: Callable[[], Awaitable[None]],
    *,
    retries: int = 3,
    base_delay: float = DEFAULT_BASE_DELAY_SECONDS,
    max_delay: float = DEFAULT_MAX_DELAY_SECONDS,
    on_retry: Optional[Callable[[int, float, BaseException], None]] = None,
) -> Optional[BaseException]:
    """执行 ``fn``，失败后按指数退避重试。

    Args:
        retries: **重试次数**（不含首次）。``retries=3`` 即最多尝试 4 次。
        base_delay: 首次重试前等待秒数，之后按 2 倍递增。
        max_delay: 单次等待上限。
        on_retry: 每次重试前的回调，参数为 (第几次重试, 等待秒数, 本次异常)。

    Returns:
        ``None`` 表示最终成功；否则为**重试耗尽时的最后一个异常**。
    """
    last_exc: BaseException | None = None
    for attempt in range(retries + 1):
        try:
            await fn()
            return None
        except asyncio.CancelledError:
            raise
        except Exception as exc:
            last_exc = exc
            if attempt >= retries:
                return last_exc
            delay = min(max_delay, base_delay * (2 ** attempt))
            if on_retry is not None:
                on_retry(attempt + 1, delay, exc)
            await asyncio.sleep(delay)
    return last_exc
```

#### `_loop` 接入重试

```python
# app/tasks/periodic_task.py
        while True:
            last_exc = await run_with_retry(
                cls._run_once,
                retries=settings.BACKGROUND_TASK_RETRY_TIMES,
                base_delay=settings.BACKGROUND_TASK_RETRY_BASE_DELAY_SECONDS,
                max_delay=settings.BACKGROUND_TASK_RETRY_MAX_DELAY_SECONDS,
                on_retry=cls._on_retry,
            )
            if last_exc is None:
                cls._on_success()
            else:
                cls._on_failure(last_exc)

            await asyncio.sleep(cls._next_delay_seconds())

    @classmethod
    def _on_retry(cls, attempt: int, delay: float, exc: Exception) -> None:
        logger.warning("%s第 %s 次执行失败，%.1fs 后重试 | error=%s",
                       cls._task_name, attempt, delay, exc)

    @classmethod
    def _on_success(cls) -> None:
        if cls._consecutive_failures:
            logger.info("%s已恢复（此前连续失败 %s 次）",
                        cls._task_name, cls._consecutive_failures)
        cls._consecutive_failures = 0
        cls._alert_sent = False

    @classmethod
    def _on_failure(cls, exc: Exception) -> None:
        """重试耗尽：记为一次「执行失败」，达到阈值则告警（恢复前只报一次）。"""
        cls._consecutive_failures += 1
        count = cls._consecutive_failures
        threshold = settings.PERIODIC_TASK_FAILURE_ALERT_THRESHOLD

        logger.warning("%s执行失败（重试耗尽，连续第 %s 次）| error=%s",
                       cls._task_name, count, exc)
        if count % 10 == 0:
            logger.exception("%s已连续失败 %s 次，保留完整堆栈", cls._task_name, count)

        if count >= threshold and not cls._alert_sent:
            cls._alert_sent = True
            logger.error(
                "[bg_task_alert]%s连续 %s 次执行失败（每次已重试 %s 次，阈值 %s），"
                "需人工介入；恢复前不再重复告警",
                cls._task_name, count,
                settings.BACKGROUND_TASK_RETRY_TIMES, threshold,
            )
```

|---|---|

| 第 2 次执行失败 | 记 2 次，不告警 |
| 第 3 次执行失败 | 记 3 次 → **告警**（恢复前只报一次） |
| 任一次执行成功 | 计数清零，告警状态解除，可再次告警 |
| 执行中重试成功 | 视为本次执行成功，计数清零 |

## 四、新增 `app/tasks/mail_poll_loop.py`

邮件轮询计时器，**只负责「什么时候调用」**，动作委托给 `MailManager._poll_once()`。

```python
"""邮件机器人轮询计时器。

调度策略与周期巡检（``PeriodicTaskManager``）同源，但**有独立开关**，
避免全局 ``PERIODIC_TASK_SCHEDULING`` 的改动连带影响邮件轮询：

* ``MAIL_POLL_SCHEDULING=auto``（默认）→ 跟随 ``PERIODIC_TASK_SCHEDULING``；
* ``MAIL_POLL_SCHEDULING=interval``   → 每 ``MAIL_POLL_INTERVAL_MINUTES``（默认 30 分钟）；
* ``MAIL_POLL_SCHEDULING=daily_times``→ 按 ``PERIODIC_TASK_DAILY_TIMES`` 的每日时刻。

典型组合：全局 ``auto``（生产按每日时刻跑巡检），邮件单独 ``interval``
→ 巡检仍按时刻，邮件保持 30 分钟一次。
"""
from __future__ import annotations

import asyncio
import logging
from contextlib import suppress
from typing import Awaitable, Callable, Optional

from app.core.config import get_settings
from app.tasks import scheduler

logger = logging.getLogger(__name__)

PollOnce = Callable[[], Awaitable[None]]


class MailPollTimer:
    """邮件轮询的计时循环（全局单例）。"""

    _task: Optional[asyncio.Task] = None

    # ==================== 生命周期 ====================

    @classmethod
    def start(cls, poll_once: PollOnce) -> None:
        """启动轮询循环（重复调用只生效一次）。"""
        if cls._task is not None:
            logger.warning("MailPollTimer 已启动，跳过重复 start")
            return
        cls._task = asyncio.create_task(cls._loop(poll_once), name="邮件轮询")
        logger.info(
            "邮件轮询已启动：模式=%s，下次执行约在 %.0f 秒后",
            cls.resolve_mode(), cls.next_delay_seconds(),
        )

    @classmethod
    async def stop(cls) -> None:
        """取消并等待轮询循环结束。"""
        if cls._task is None:
            return
        cls._task.cancel()
        with suppress(asyncio.CancelledError):
            await cls._task
        cls._task = None
        logger.info("邮件轮询已停止")

    # ==================== 调度 ====================

    @staticmethod
    def resolve_mode() -> str:
        """当前生效的调度模式（默认跟随全局）。"""
        s = get_settings()
        return scheduler.resolve_following(
            s.MAIL_POLL_SCHEDULING,
            s.PERIODIC_TASK_SCHEDULING,
            is_production=str(s.environment).lower() == "production",
        )

    @staticmethod
    def next_delay_seconds() -> float:
        """下一次轮询的等待秒数。"""
        s = get_settings()
        return scheduler.delay_seconds(
            MailPollTimer.resolve_mode(),
            dev_interval=s.PERIODIC_TASK_DEV_INTERVAL_SECONDS,
            interval_seconds=s.MAIL_POLL_INTERVAL_MINUTES * 60,
            daily_times=s.PERIODIC_TASK_DAILY_TIMES,
        )

    @staticmethod
    def max_interval_seconds() -> float:
        """当前模式下相邻两次轮询的最大间隔，用于心跳阈值推导。"""
        s = get_settings()
        return scheduler.max_interval_seconds(
            MailPollTimer.resolve_mode(),
            dev_interval=s.PERIODIC_TASK_DEV_INTERVAL_SECONDS,
            interval_seconds=s.MAIL_POLL_INTERVAL_MINUTES * 60,
            daily_times=s.PERIODIC_TASK_DAILY_TIMES,
        )

    # ==================== 内部循环 ====================

    @classmethod
    async def _loop(cls, poll_once: PollOnce) -> None:
        """先等一个周期，再反复调用 ``poll_once``。"""
        await asyncio.sleep(cls.next_delay_seconds())

        while True:
            try:
                await poll_once()
            except asyncio.CancelledError:
                raise
            except Exception:
                # 与 PeriodicTaskManager 一致：失败不退出循环，下一轮重试
                logger.exception("邮件轮询失败，将继续重试")
            await asyncio.sleep(cls.next_delay_seconds())
```

## 十一、修复：中断节点吞掉 `GraphInterrupt`

### 11.1 现象

`get_candidate_email_reply_node`（`app/workflow/candidate_nodes/check_availability_node.py`）
是「等待候选人回邮件」的中断节点，但**状态图从来没有真的暂停过**：
`Command(resume=邮件正文)` 传进来的内容永远收不到，`candidate_email_reply` 恒为 `""`。

### 11.2 根因

原实现：

```python
    try:
        reply = interrupt(value=None)
    except Exception as e:
        logger.error("解析候选人邮件回复失败: %s", e)   # ← 语义也错了
        reply = ""
```

`interrupt()` 的机制是**用抛异常实现挂起**（`langgraph/types.py:1038`）：

```python
    # no resume value found
    raise GraphInterrupt((Interrupt.from_ns(value=value, ...),))
```

继承链是 `Exception ← GraphBubbleUp ← GraphInterrupt`，所以 `except Exception`
**一定会捕获它**——中断信号被吞掉，节点正常返回，图直接往下走到 `check_availability`。

实测对照（最小图，同一 venv）：

```text
== A. try/except 版（原实现）==
    [except 捕获到] langgraph.errors.GraphInterrupt
   首轮 stream: [{'n': {'reply': ''}}]
   是否挂起（出现 __interrupt__）: False

== B. 裸调用版（修复后）==
   首轮 stream: [{'__interrupt__': (Interrupt(value=None, id='a649eb5e...'),)}]
   是否挂起: True
   恢复后: [{'n': {'reply': '我明天下午3点方便'}}]
```

### 11.3 修复

```python
async def get_candidate_email_reply_node(state: CandidateRecruitmentState):
    """中断节点：等待候选人邮件回复。

    ``interrupt()`` 的机制是**抛异常``：节点内首次调用会抛 ``GraphInterrupt``
    让整张图挂起，客户端用 ``Command(resume=...)`` 恢复后，同一行才 return 恢复值。

    因此这里**不能**用 ``except Exception`` 包住它——那会把中断信号吞掉，
    图直接往下跑（``candidate_email_reply`` 恒为空），恢复接口永远收不到内容。
    同理，本节点也**不能**加 ``@node_error_wrapper``：它会把 ``GraphInterrupt``
    落在「未知异常」分支包装成 ``AppException``，同样破坏中断。
    """
    cid = state["candidate"].id
    logger.info("[email_reply] waiting for candidate reply | candidate_id=%s", cid)
    logger.info(
        "[email_reply] resume thread before interrupt | candidate_id=%s | thread_id=%s",
        cid, state["candidate"].email,
    )
    # 不要 try/except：让 GraphInterrupt 原样冒泡到 LangGraph 运行时
    reply = interrupt("candidate_email_reply")
    if reply is None:
        reply = ""

    return {
        "candidate_email_reply": reply,
        "current_stage": "email_reply",
    }
```

顺带修掉两处：

- `interrupt(value=None)` → `interrupt("candidate_email_reply")`：`value` 是展示给
  客户端的上下文，`None` 等于没给（与 `docs/interview_questions.md` 的描述一致）。
  resume 值按**顺序**匹配（`scratchpad.interrupt_counter()`），改 `value` 不影响恢复。
- 删掉语义错误的「解析候选人邮件回复失败」日志——异常来自中断机制，不是解析。

### 11.4 为什么这个节点不能加 `@node_error_wrapper`

`app/workflow/error_handler.py:70`：

```python
except Exception as e:
    logger.error("[error_wrap] %s unexpected exception ...", ...)
    raise AppException(f"节点 {node_func.__name__} 未知异常: {e}") from e
```

`GraphInterrupt` 不是 `BusinessException` / `ExternalServiceError`，会落进这个分支
被包装成 `AppException`，同样破坏中断。所以本节点是**少数不该加该装饰器的节点**
（`docs/interview_questions.md` 把它列为「改进点」，那条建议其实是个坑）。

### 11.5 回归测试（`tests/test_email_reply_interrupt.py`，3 条）

```python
@dataclass
class _Candidate:
    """可序列化的候选人替身（checkpointer 要序列化 state）。"""
    id: str
    email: str

class _State(TypedDict):
    candidate: _Candidate
    candidate_email_reply: Optional[str]
    current_stage: str

async def _wait_reply(state: _State) -> dict:
    """用测试自己的 schema 包装真实节点。

    不能直接把 ``get_candidate_email_reply_node`` 注册进图：它的形参标注是生产用的
    ``CandidateRecruitmentState``，LangGraph 会把那个 schema 也加进来，与测试的
    ``candidate`` channel 冲突（"already exists with a different type"）。
    """
    return await get_candidate_email_reply_node(state)  # type: ignore[arg-type]

def _build_graph():
    builder = StateGraph(_State)
    builder.add_node("wait_reply", _wait_reply)
    builder.add_edge(START, "wait_reply")
    return builder.compile(checkpointer=InMemorySaver())

async def test_interrupt_node_pauses_and_resumes():
    graph = _build_graph()
    config = {"configurable": {"thread_id": uuid.uuid4().hex}}

    first = [chunk async for chunk in graph.astream(_state(), config)]
    assert any("__interrupt__" in chunk for chunk in first)      # 必须挂起

    resumed = [chunk async for chunk in graph.astream(Command(resume="我明天下午3点方便"), config)]
    assert resumed[-1]["wait_reply"]["candidate_email_reply"] == "我明天下午3点方便"

def test_interrupt_node_works_without_try_except():
    """反向对照：GraphInterrupt 确实会被 except Exception 捕获——这就是根因。"""
    from langgraph.errors import GraphInterrupt
    assert issubclass(GraphInterrupt, Exception)
```

> 节点是 **async**，必须用 `astream`；`state` 里的占位对象要**可序列化**
> （用 dataclass，不能用 `SimpleNamespace`，否则 checkpointer 序列化失败）。

## 十三、LLM 客户端懒加载（`app/agents/llms.py`）

### 13.1 现象

跑测试时两个文件**在收集阶段**就报错，不是断言失败：

```text
ERROR collecting tests/test_graph_routes.py
ERROR collecting tests/test_intent.py
E   httpx2.InvalidURL: Invalid port: ':1]'
```

顺着查下去，影响面比「两个测试跑不了」大得多——**整个应用起不来**：

```bash
$ python -c "import app.main"
httpx2.InvalidURL: Invalid port: ':1]'
```

导入链（每一环都只是在 `import`，没有任何业务调用）：

```text
app/main.py:13  → routers/__init__.py:6 → candidate_router.py:21
→ candidate_ser.py:11 → ocr_tasks.py:5 → agents/resume.py:7
→ agents/llms.py:10（构造 ChatOpenAI）→ langchain_openai 建立 HTTP 客户端 → ✗
```

### 13.2 根因：环境层 × 代码层

**环境层（触发条件）**：宿主机 `NO_PROXY` 写成

```text
localhost,.localhost,127.0.0.1,127.0.0.0/8,[::1],::1
```

IPv6 回环带了方括号。方括号是 **URL 里**消歧端口用的记法（`http://[::1]:8080`），
而 `NO_PROXY` 的条目规范是**裸地址** `::1`。httpx 的解析流程：

```python
# httpx/_utils.py :: get_environment_proxies()
elif is_ipv6_hostname(hostname):      # "[::1]" → False（它期望裸地址）
    ...
else:
    mounts[f"all://*{hostname}"] = None   # → "all://*[::1]"，兜底给域名后缀匹配用
```

`URLPattern("all://*[::1]")` 按端口规则取最后一个冒号之后 → `:1]` → `InvalidURL`。

实测四种写法：

| `NO_PROXY` 片段 | 构造客户端 |
|---|---|
| `localhost,127.0.0.1,::1` | OK |
| `localhost,127.0.0.0/8,::1`（去掉括号项） | OK |
| `[::1]` | **FAIL** `Invalid port: ':1]'` |
| `::1`（裸写） | OK |

**代码层（放大条件）**：`ChatOpenAI` 写在模块顶层，构造即建连。一个只在「真正调用
模型」时才该出错的配置问题，被前置到了「只要 `import` 就炸」。

### 13.3 为什么不是依赖问题

venv 里 `httpx==0.28.1` 与 `httpx2==2.13.1` **并存**（`openai>=3` 换用了 API 同名的
`httpx2`，`app/core/http_client.py` 仍用 `httpx`），两者**都**失败并报同一个错——
同一段代理解析逻辑两边一致。所以升级、降级、换库都解决不了。

另外 `NO_PROXY` 不在注册表（`HKCU\Environment`、`HKLM\...\Environment` 均无此值），
是会话注入的。意味着：同事机器和 CI 不一定复现，但**谁踩到谁全停**。

### 13.4 改法：工厂函数 + `lru_cache`

```python
# 改前（模块顶层，import 即建连）
qwen_llm = ChatOpenAI(model="qwen3.8-max", base_url=..., api_key=api_key)
deepseek_llm = ChatOpenAI(model="deepseek-v4.1-flash", base_url=..., api_key=api_key)
llm = init_chat_model("deepseek-v4.1-flash", ...)     # 全仓库无人引用

# 改后（首次使用才建连，进程内单例）
@lru_cache(maxsize=1)
def get_deepseek_llm() -> ChatOpenAI:
    """主模型。"""
    return _chat_model(PRIMARY_MODEL)

@lru_cache(maxsize=1)
def get_qwen_llm() -> ChatOpenAI:
    """备用模型：主模型失败时由 RunnableWithFallbacks / ModelFallbackMiddleware 接管。"""
    return _chat_model(FALLBACK_MODEL)
```

`BASE_URL` / `PRIMARY_MODEL` / `FALLBACK_MODEL` 提为模块常量（原先是 3 份重复字面量）。
顺带删掉 `llm = init_chat_model(...)`——没有任何消费方，而且它同样在导入期建连，
留着就等于留一个后门。

**消费点**（5 个文件，5 处导入 + 13 处引用）：

| 文件 | 引用位置 | 备注 |
|---|---|---|
| `app/agents/candidate.py` | 5 处 | `score_for_candidate` 工具、`CandidateProcessAgent.ainvoke` |
| `app/agents/resume.py` | 2 处 | 已在 `_get_agent()` 里，天然延迟 |
| `app/workflow/candidate_nodes/scoring_node.py` | 2 处 | `_build_score_llm()` 内 |
| `app/workflow/candidate_nodes/check_availability_node.py` | 2 处 | `_build_time_llm()` 内 |
| `utils/emailbot/intent.py` | 2 处 | `_get_intent_llm()` 内，已有全局缓存 |

结构本来就很配合：三处 `with_structured_output` 和两处 `create_agent` 都包在
**运行时才调用**的 builder 函数里，改的只是「模型实例从哪来」。

### 13.5 坑：模块 `__getattr__` 单独用没有

PEP 562 的模块级 `__getattr__` 看起来是更省事的兼容写法（保留 `qwen_llm` 这个名字，
第一次访问才构造）。**但对 `from X import name` 无效**——这种写法在消费方
`import` 的那一刻就会触发 `__getattr__`，构造照样发生在收集期/启动期。

必须让消费方在**函数体内**取值，所以旧的模块级名字直接删掉，不留兼容别名。

### 13.6 边界：失败点后移 ≠ 失败消失

改完之后：

- `import app.main`、pytest 收集、`alembic`、`scripts/*` 都不再受宿主代理配置影响；
- 真正**调用** LLM 时如果环境依旧不合法，还是在 `get_deepseek_llm()` 抛同一个
  `InvalidURL`。这是**期望行为**——错误回到它真正的原因上。所以：
  - 本机仍建议把 `NO_PROXY` 的 `[::1]` 去掉（保留裸 `::1`）；
  - `app/core/http_client.py::get_http_client()` 本来就是懒加载，在同样的环境下
    **运行期**会炸（钉钉授权、OCR、发信都走它），本次未动。彻底免疫需要显式
    决策「是否读宿主代理」：给 `ChatOpenAI` 注入 `http_client` / `http_async_client`
    （`trust_env=False`，注意要用 `langchain_openai._compat.httpx` 拿 SDK 实际对应的库），
    并给 `get_http_client()` 同样设置。**属于后续项，本次没做。**
- 缺 `DASHSCOPE_API_KEY` 的行为也变了：以前 `import` 就 `OpenAIError: Missing
  credentials`（实测空 key 确实构造失败），现在推迟到首次调用模型。


### 15.2 `check_am_or_pm` 的 naive / aware 比较（#8）



```python

    # datetime.combine 默认产出 naive，直接比较会抛

    window_start = datetime.combine(proposed_dt, win_start, tzinfo=proposed_dt.tzinfo)
```

#### 15.5.1 一个容易误解的点：这不是「给回调加鉴权」

回调端点**至今没有** `current_user` 依赖，参数只有 `get_db` 与 `get_redis`：

```python
async def dingtalk_callback(
    session: Annotated[AsyncSession, Depends(get_db)],
    state: str, code: str | None = None, authCode: str | None = None,
    error: str | None = None,
    r: Redis = Depends(get_redis),
):
```

这是**有意的**，而且不可能改成别的：回调是钉钉服务器 302 甩过来的浏览器 GET，
而本项目鉴权只有一条路——`OAuth2PasswordBearer` 读 `Authorization: Bearer`
（`auth.py:133`），token 存在前端 `localStorage`（`stores/user.ts:32`）。
浏览器自动跟随重定向时不会带上它，全项目也没有任何 cookie/session 机制
（`set_cookie` / `SessionMiddleware` 零命中）。加 `get_current_user` 只会让流程 100% 跑不通。

所以本节的改动改变的不是「怎么鉴权」，而是**「身份从哪来」**：

| | 旧 | 新 |
|---|---|---|
| `user_id` 来源 | 调用方在 URL 里自带的 `state` 参数 | 服务器签发的 nonce 反查 |
| 性质 | **自报身份**——匿名请求者可任意填写 | **能力凭证**——只能证明「我持有服务器发给某人的那次凭证」 |
| 攻击者能绑谁 | 任意他人 | 只能绑自己 |

**恰恰因为端点无鉴权，才更不能让请求者自述身份。** OAuth 2.0 用 `state`
解决的就是这个问题（RFC 6749 §10.12），它不是鉴权手段，而是把发起端已经完成的
鉴权「延伸」到回调端的手段：

```text
① 前端带 Bearer 调 /dingtalk/authorize          ← 鉴权在这里发生
② 服务端生成 nonce，记下 nonce → 该 user_id       ← 信任关系在这里建立
③ 浏览器 → 钉钉 → 302 回 /callback?state=nonce&code=...
④ 回调端用 nonce 反查②里登记的用户               ← 只需证明「这次回调对应②」
```

#### 15.5.2 反证：服务层一直按 user_id 组织，旧写法是靠巧合

排查中发现 `candidate.py:162` 早就这么调用：

```python

```

`dingtalk_ser` 内部的 Redis 键 `dingtalk:user_actoken:{state}` / `dingtalk:user_retoken:{state}`
**一直是按 user_id 拼的**，形参名 `state` 属于历史误称。旧 router 把 OAuth 的 `state`
原样透传进去不会出错，只是因为 `state` 恰好等于 user_id——**这个巧合本身就是漏洞**。
改后 router 与 `candidate.py` 传的是同一种东西，两个概念被正确解耦。

#### 15.5.3 补一个原子性缺陷（本次追加）

初版把「读」和「销」分成两条命令，中间有窗口，并发重放同一个 nonce 时
两个请求都能读到有效 `user_id`：

```python

-    await r.delete(state_key)          # ← GET 与 DELETE 之间可被插入
```

### 15.6 reducer 让「显式清空」失效（#11）

```python
- assign_state_property = lambda x, y: y if y is not None else x
+ def assign_state_property(left, right):
+     return right
```

关键在于 reducer **只在节点确实写了这个字段时**才被调用——「没写」本来就由
LangGraph 的 channel 默认保留旧值，不需要 `None` 兜底。把 `None` 当成「不写」，
代价是显式清空全部失效。

实际受影响的是人工重试（`candidate_status_ser.py:179-186`）：

```python
                    "error_message": None,
                    "error_stage": None,
                    "negotiation_round": 0,
                    "candidate_email_reply": None,
                    "proposed_interview_time": None,
                    "email_sent": False,
                    "email_sent_at": None,
```

注释写的是「清理错误状态」「重置协商状态」，但在旧 reducer 下前四项
（`None` 值）**全部没被清掉**，上一轮的脏 `candidate_email_reply`
会直接参与新一轮路由判断。`email_invite_node` 无空闲时段分支写的
`"email_sent_at": None` 同理——它想表达「这条没有超时起点」，旧写法却保留了旧时间戳。

实测确认修复后的两种语义都正确：

```text

```

### 15.7 `FakeRedis.eval` 忽略 Lua，限流测试空过（#12）

原实现完全不看 `script` 参数，无条件做一次 GETDEL：

```python
    async def eval(self, script: str, numkeys: int, *keys_and_args: Any) -> Any:
        key = keys_and_args[0]
        value = self.store.get(key)
        ...
```

这对 `auth._CONSUME_REFRESH_LUA`（GET + DEL）**碰巧**语义一致，
但 `rate_limit._SLIDING_WINDOW_LUA`（ZREMRANGEBYSCORE / ZCARD / ZADD / PEXPIRE）
被当成「取一个字符串 key」——限流从未在测试里真正生效过。

用旧 FakeRedis 实测滑动窗口：

```text
旧 FakeRedis 下的结果: [False, False, False, False]
能否发现超限? False
```

四次调用**全被拒**，而生产行为是「前三次放行、第四次拒绝」。
任何 `assert hit(...) is True` 都会在这里失败，所以此前根本没有这类断言。

改为按脚本文本分派到 Python 等价实现，并补 ZSET 命令：

```python
    async def eval(self, script: str, numkeys: int, *args: Any) -> Any:
        keys = list(args[:numkeys])
        argv = list(args[numkeys:])

        if "ZREMRANGEBYSCORE" in script:
            # 滑动窗口限流：清理窗口外成员 → 计数 → 未超限则记录本次
            key = keys[0]
            now, window, limit = float(argv[0]), float(argv[1]), int(argv[2])
            member = argv[3]
            await self.zremrangebyscore(key, 0, now - window)
            if await self.zcard(key) < limit:
                await self.zadd(key, {member: now})
                return 1
            return 0

        if "redis.call('GET'" in script:
            # 原子消费（refresh token）：GET 到就 DEL，否则 nil
            value = self.store.get(keys[0])
            if value is not None:
                del self.store[keys[0]]
                return value
            return None

        raise AssertionError(
            "FakeRedis 未实现该 Lua 脚本的等价语义，请补实现而不是让它静默通过"
        )
```

最后那句 `raise` 是这个改动的重点：**未知脚本必须失败**，
否则下次再加一段 Lua，测试还会继续静默通过。

### 18.1 候选人「同意原时间」被判成协商失败

**现象**：候选人回复「可以，就这个时间」，两天后收到《协商超时》邮件、状态变「协商超时」。

**根因**：`app/agents/prompts.py` 对 `ProposedTime` 的约定是——

```text
同意原时间：候选人同意之前的邀约，将 confirm 设为 True，refused 设为 False，proposed_time 和 exactly 置空。
```

而 `check_availability_node` 里 `confirm` **只出现在 `logger.info` 里，没有任何消费分支**：

```python
    if pt.refused:                       # 拒绝 → refused
        ...
    if not pt.proposed_time:             # 「同意原时间」正是 proposed_time == ""
        logger.info("[check_avail] no time proposed | candidate_id=%s", cid)
        return await can_not_find_available_time(state)   # ← 当成「没给时间」，轮次 +1
```

**完整链路**（§十一 修好中断之后才成立）：

```text
候选人「同意」→ confirm=True / proposed_time="" → 走「未提供时间」→ negotiation_round=1
→ 路由回到 get_candidate_email_reply_node → 挂起等一封不会再来的邮件
→ 48 小时超时巡检注入 EMAIL_REPLY_TIMEOUT → negotiation_expired → 状态「协商超时」+ 超时邮件
```

**修复**（`check_availability_node.py`）：

```python
    # 候选人同意原时间：state["proposed_interview_time"] 是首次邀请时从面试官空闲时段
    # 里挑出来的，无需再查一次钉钉，直接按「可用」放行进 confirm 分支。
    # 缺这个分支时「可以，就这个时间」会因 proposed_time 为空被判成协商失败，
    # 耗尽轮次后走到 negotiation_expired。
    if pt.confirm:
        logger.info("[check_avail] candidate accepted original time | candidate_id=%s", cid)
        return {
            "candidate_email_reply": REPLY_TIME_AVAILABLE,
            "current_stage": "check_availability",
        }
```

四个设计点：

| 决定 | 理由 |
|---|---|
| 放在 `if pt.refused:` **之后** | 提示词禁止两个标记同时为真；真同时出现时按拒绝处理，宁可少排一场面试也不要凭空安排一场 |
| **不**回写 `proposed_interview_time` | reducer 是「后写覆盖」（§15.6），不写即沿用首次邀约的时间，正是「同意原时间」的语义 |
| **不**再查一次钉钉空闲时段 | 该时间本来就是 `email_invite_node` 从空闲段里挑的；确认阶段再查会多一次外部调用，且此刻查不到反而要重新协商，与候选人收到的确认邮件矛盾。若日后要求二次校验，应显式改这段并同步测试 |
| 返回值用 `REPLY_TIME_AVAILABLE` 常量 | 与路由函数 `route_after_check_availability` 的比较值同源（§15.3 同类问题） |

**测试**：`tests/test_confirm_branch.py` 5 个——分支取值、不触碰钉钉、节点输出与路由的契约
（合并后必须落到 `confirm`）、`confirm`/`refused` 同时为真按拒绝、既不同意也没给时间仍继续协商。

### 18.2 `email_invite` 的出边没有错误守卫

**根因**：`build_candidate_graph` 里 5 条出边，4 条走
`add_conditional_edges(..., _with_error_check(...), {... "error": "error"})`，只有这一条是静态边：

```python
    # === 邮件发送后等待候选人回复 ===
    graph.add_edge("email_invite", "get_candidate_email_reply_node")
```

`email_invite_node` 发信失败抛 `EmailSendError`（`app/core/exceptions.py:87`，`BusinessException`
子类），被 `@node_error_wrapper` 转成一次**普通状态更新**——异常不出节点：

```python
        except BusinessException as e:
            return {"current_stage": "error", "error_occurred": True,
                    "error_message": e.message, "error_stage": state.get("current_stage")}
```

静态边不看 `error_occurred`，于是照旧进入中断点。守卫只挂在出边上，所以
`error` 节点、`trigger_manual_retry`、`MANUAL_PASSED` 全套兜底机制**都进不来**：

```text
候选人状态：AI 筛选成功（error_node 没执行，不会变 PROCESSING_ERROR）
current_stage：email_reply（被中断点覆盖）
email_invite_sent_at：NULL（_mark_invite_sent 在发信之后，没跑到）
```

最后一条尤其关键：超时巡检的查询条件是 `email_invite_sent_at.is_not(None)`，
所以这个候选人**连巡检都捞不到**，会永久停在「AI 筛选成功」。

> 先前口头描述里说过「`current_stage` 停在 `email_invite`」，不准确：进入中断点后
> `get_candidate_email_reply_node` 会把它写成 `email_reply`。

**修复**（`candidate_graph.py`）：

```python
def _route_after_email_invite(state: CandidateRecruitmentState) -> str:
    """email_invite 之后的路由。...（docstring 记录上面那条链路）"""
    cid = state["candidate"].id
    logger.info("[route_email_invite] candidate_id=%s | dest=get_candidate_email_reply_node", cid)
    return "get_candidate_email_reply_node"

    # === 邮件发送后等待候选人回复（条件边：发信失败要在进入中断点之前分流到 error） ===

        "email_invite",

            "get_candidate_email_reply_node": "get_candidate_email_reply_node",
            "error": "error",

    )
```

**同类缺口：`confirm → END` 同样是静态边**（`confirm_node` 也带 `@node_error_wrapper`，
建日程或发确认邮件失败时会写 `error_occurred=True`）。本轮**有意不改**：
`confirm_node` 非原子（见 §附），失败时数据库/钉钉日程/确认邮件可能只成功了一部分，
直接分流到 `error` 后 HR 点「人工通过/重试」会重跑 `email_invite`，
产生第二场日程与第二封邀请邮件。这一条应与 `confirm_node` 的幂等改造
（用 `interview_created` 标记跳过已完成的副作用——该字段现在写了但无人读）一起做。

**测试**：`tests/test_email_invite_guard.py` 6 个——用**真实** `email_invite_node`

### 18.3 候选人写接口越权

**根因**：仓库里已经有按用户划界的取人方法 `CandidateRepo.get_for_user()`
（`_visible_stmt`：superuser 全量 / HR 取所管部门 / 其他人取自己发布的职位），
列表与两个下载接口都在用，但两个**写**接口各走各的：

| 接口 | 修复前取人方式 | 修复前权限依赖 |
|---|---|---|
| `PATCH /candidate/{id}/status` | `get_by_id(candidate_id)` | 仅「是 HR」 |
| `DELETE /candidate/{id}` | 无——`delete_candidate(id)` 直接删 | 仅「是 HR」 |

利用面：任意 HR（不需要是该候选人的面试官或部门管理员）可改状态、
可造出一条 `interviewer_id=自己` 的面试记录，也可删掉别人部门的候选人及其评分与面试记录。

**修复**（`candidate_router.py`，两处都换成已有的可见性判定）：

```python
        # 用 get_for_user 而不是 get_by_id：可见性判定要和列表/下载接口一致，
        # 否则任何登录用户凭 candidate_id 就能改写他人候选人的状态、新建面试记录。
        # 「不存在」与「无权访问」返回同一状态，避免被用来枚举候选人 id。
        candidate = await candidate_repo.get_for_user(candidate_id, current_user)
        if not candidate:
            raise HTTPException(status_code=404, detail="候选人不存在或无权访问")
```

```python
        # delete_candidate 只按 id 删，不看归属：不先做可见性校验的话，
        # 任何 HR 都能删除其它部门的候选人。
        if await candidate_repo.get_for_user(candidate_id, current_user) is None:
            raise HTTPException(status_code=404, detail="候选人不存在或无权访问")
        deleted = await candidate_repo.delete_candidate(candidate_id)
```

未改的两处，说明清楚避免误会：

- 校验与删除放在**同一个** `async with session.begin()` 里，不存在「校验通过后才被删」的
  竞态窗口需要额外处理（同事务内可见性判定与后续写入用同一份数据快照）。
- `PATCH` 里 `create_interview(interviewer_id=current_user.id)` 保持原样：那是「HR 给自己排面试」
  的既有语义，不是越权。

**测试**：`tests/test_candidate_ownership.py` 6 个——不可见时**零写入**（连 `get_by_id` 都不许再出现，
替身里直接 `raise AssertionError`）、可见时正常放行且留审计、两个接口文案一致。

## 十九、第五轮：时间处理统一

### 19.1 为什么是换位置，而不只是改个名

旧模块 `utils/time_ISO8601_datatime.py` 有三个问题，只有第一个能靠改名解决：

1. `datatime` 是拼写错误，而 `ISO8601` 只描述其中两个函数，另外四个和时间格式化无关；
2. 它放在 `utils/`（那里是 `PDFser` / `ocr_service` / `emailbot` 这类外部能力封装），
   但它约束的其实是**全项目的数据表示形式**——和 `config.py`、`db.py`、`auth.py`
   是同一层的东西，于是挪到 `app/core/time.py`；
3. 真正的问题不是名字：**它只提供了半个方向的换算**，剩下的靠调用方手写，
   每个手写点都是一次「naive 和 aware 谁在比较谁」的重新决策。

统一后的模型只有一句话：**内存里流转的 datetime 一律是 aware 北京时间；
只有跨两道边界时才改变表示形式**——进数据库剥掉时区（存北京时间的 naive 数值），
出网络边界格式化成 ISO-8601 字符串。

### 19.2 新模块的出入口

| 名称 | 输入 | 输出 | 用在哪 |
|---|---|---|---|
| `BEIJING_TZ` | — | `timezone(timedelta(hours=8), "Asia/Shanghai")` | 唯一的 tzinfo 常量 |
| `BEIJING_TZ_NAME` | — | `"Asia/Shanghai"` | 钉钉请求体里的 `timeZone` |
| `now_beijing()` | — | aware | 业务计算、和钉钉时段比较 |
| `db_now()` | — | **naive** | ORM 列默认值、查询条件 |
| `to_naive_beijing(dt)` | aware / naive | naive 北京时间 | 写库前 |
| `from_naive_beijing(dt)` | naive / aware | aware | 库里读出来要参与计算、时间字符串解析 |
| `to_iso8601(dt)` | aware / naive | `"…+08:00"`，无微秒 | 钉钉查询参数、日程 `dateTime` |
| `from_iso8601(s)` | ISO 字符串 | aware 北京时间 | 钉钉返回的 `start/end.dateTime` |

约定：naive 输入一律**按北京时间理解**（只剥/只贴时区，不改数值），`None` 原样透传；
JWT 与审计日志继续走 UTC（`app/core/auth.py`、`app/core/audit.py`），不归本模块管。

删掉的东西：

- 两个「向后兼容别名」`datetime_to_iso8601_beijing` / `iso8601_to_datetime_beijing`
  ——只有 `dingtalk_ser.py` 在用，而正名 `to_iso8601` 一直没人改，别名反而成了主名；
- `from_iso8601` 里的 `Z → +00:00` 预处理、`re.sub` 微秒补零、双层 `try` 的「空格→T」回退：
  `requires-python >= 3.13`，`datetime.fromisoformat` 原生支持 `Z` 与任意位数的小数秒。
  实测 `"2026-11-20T02:30:00Z"` → `2026-11-20T10:30:00+08:00`，
  `"2026-11-20T10:30:00.123456+08:00"` 微秒保留；
- `to_naive_beijing` 对 naive 分支的 `dt.replace(tzinfo=None)`（本来就是 naive，等于空操作）。

**为什么仍是固定偏移而不是 `ZoneInfo("Asia/Shanghai")`**：中国 1991 年后不再实行夏令时，
两者对现在与将来的时间戳完全等价；而 `tzdata` 不在 `pyproject.toml` 依赖里——
本机 `zoneinfo` 能用是因为命中了系统时区库（实测可解析），换成
`python:3.13-slim` 这类不带 tzdata 的镜像就是 `ZoneInfoNotFoundError`。
少一个环境依赖，比「看起来更标准」值钱的。

### 19.4 顺带修掉的两个缺陷

**① 钉钉空闲时段查询起点丢时区、且带着小时**（`dingtalk_ser.py:277`）

改前：

```python
start_datetime = datetime(year=start_time.year, month=start_time.month,
                          day=start_time.day, hour=start_time.hour) + timedelta(days=time_delta)
```

重新构造 `datetime` 而不是 `replace`，tzinfo 直接没了；`hour=start_time.hour`
又让窗口左端带上了「当前小时」。走默认参数的是 `email_invite_node`
（`start_time=None` → `now_beijing()`，`time_delta=1`）：17:xx 触发时日历只从
**次日 17:00** 开始拉忙碌时段，而 `find_available_slot` 的计算窗口从次日 00:00 开始
——次日上午真实存在的会议没被拉回来，于是被当成空档推给候选人。
这和 §15「查询窗口与计算窗口对齐」是同一类问题，只是这次藏在默认参数路径上。

改后：`(start_time + timedelta(days=time_delta)).replace(hour=0, minute=0, second=0, microsecond=0)`，
保持 aware，两个窗口的左端对齐。`check_availability_node` 那条路径本来就传
00:00 起算 + `time_delta=0`，改前后等价。

**② 确认邮件把 LLM 传入的时间原文回显给候选人**（`app/agents/candidate.py:290`）

`interview_datetime_str` 是模型给的字符串，偏移量是什么就显示什么；
改成解析后按北京时间格式化：`2026-11-20 10:30（北京时间）`。

### 19.5 没有变的：库里仍然是 naive 北京时间

`candidates.*_at` 依旧是 `TIMESTAMP WITHOUT TIME ZONE`，存「北京时间的 naive 数值」——
**零迁移、零回填**，这是本轮敢一次性改 13 个文件的前提。
列形态由测试锁住（`col.type.timezone is False` + default/onupdate 产出 naive），
将来谁想把列改成 `timestamptz`，会先在这里红一条，而不是在生产上撞比较异常。

真要多时区面试官，需要 alembic 改列 + 历史数据回填 + 全链路比较改写，另开一轮。
